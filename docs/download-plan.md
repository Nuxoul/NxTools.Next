## 产品形态

下载器是 NxTools.Next 主窗口中的正式模块，包含紧凑任务列表、分类/状态导航、任务详情、新建下载、
独立单任务进度窗口、完成窗口、队列和设置。浏览器扩展与 CLI 是同一个下载引擎的外部调用端，
不拥有下载状态。

界面遵守当前 NxTools.Next 的视觉语言：

- Zed 式石墨色背景层级、低对比边界和清晰聚焦态；
- ABDM 式高信息密度与紧凑任务行；
- 不使用大片留白、对称卡片墙或无功能按钮；
- 进度变化合并后再刷新 GPUI，空闲时不持续请求动画帧；
- 长列表虚拟化，任务详情和分段视图按需渲染。

## 领域模型

| 术语 | 定义 | 不变量 |
| --- | --- | --- |
| 下载请求 `DownloadRequest` | 用户、浏览器或 CLI 提交的原始下载意图 | 尚未探测，不等于持久化任务 |
| 下载任务 `DownloadTask` | 持久化的下载聚合对象 | 拥有稳定 ID、状态、目标和恢复信息 |
| 传输方案 `TransferPlan` | 探测后生成的协议、资源验证器和分段计划 | 服务端资源变化后必须重新验证 |
| 分段 `Segment` | 可持久化的字节范围或媒体分片 | HTTP 字节范围不得重叠或越界 |
| 连接 `Connection` | 一次运行时网络连接 | 不持久化；数量不等于分段数量 |
| 尝试 `Attempt` | 一次任务或分段执行尝试 | 记录错误分类、重试次数和退避 |
| 队列 `Queue` | 排序、并发和默认策略 | 不负责执行协议细节 |
| 计划 `Schedule` | 决定任务何时有资格进入调度 | 与传输状态分离 |
| 产物 `Artifact` | 临时文件、最终文件或媒体轨道 | 只有原子提交后才算完成 |

UI 中使用“连接上限”，不再把活动连接称为“线程”。配置的连接上限、当前活动连接数和持久分段数量
是三个不同指标。

建议的传输状态：

```text
Created -> Probing -> Waiting -> Downloading -> Finalizing -> Verifying -> Completed
                         ^            |
                         |            v
                       Paused <-------+

任意可执行状态 -> Failed / Cancelled
```

队列归属、计划时间、自动暂停原因和重试退避是独立字段。UI 可以把它们组合成“计划中”“排队中”等
展示文案，但不得把所有调度信息继续堆进状态枚举。

## 模块与职责

### Rust：下载核心

新增深模块 `nxtools-download`，外部接口保持为少量命令和快照：

- `probe(request)`
- `submit(request)`
- `command(task_id, command)`
- `snapshot(query)`
- `subscribe(events)`

实现内部负责：

- HTTP/HTTPS 探测、重定向、请求上下文和代理；
- Range 验证、分段、动态拆分、连接协调和回退；
- 重试、退避、停滞检测、速度限制和磁盘写入；
- 队列、计划、优先级和并发准入；
- SQLite 任务/分段/设置存储及崩溃恢复；
- 临时产物、原子提交、校验和清理；
- 后续 HLS/DASH 协议适配。

协议实现、数据库表和 HTTP 客户端类型不暴露给 GPUI、CLI 或 C#。

### Rust：桌面与 CLI 调用端

`NxTools.exe`：

- 拥有下载应用状态和 GPUI 呈现；
- 把用户动作转换成引擎命令；
- 消费有界、合并后的任务事件；
- 不直接实现 HTTP 或写分段文件。

建议新增 `NxTools.Cli.exe`，也可在打包策略允许时使用同一二进制的 `cli` 子命令。首版命令：

```text
nxtools download add <url> [--dir <path>] [--name <name>] [--header <k:v>]
nxtools download list [--active|--completed|--failed] [--json]
nxtools download show <id> [--watch] [--json]
nxtools download pause <id...>
nxtools download resume <id...>
nxtools download cancel <id...>
nxtools download remove <id...> [--delete-file]
```

CLI 默认连接已运行的桌面实例；桌面未运行时，可启动无窗口引擎宿主或明确返回可诊断错误，具体策略在
阶段 1 冻结。CLI 必须提供稳定退出码和机器可读 JSON，供集成测试调用。

### C#：Windows 适配器

C# 仅负责 Windows 专属能力：

- 文件夹/文件选择窗口；
- Shell 打开、定位和完成通知；
- 浏览器 Native Messaging 注册与 Windows 注册表；
- Windows 系统代理、凭据或证书存储适配；
- 关机等完成后系统动作。

C# 不执行下载、不保存任务、不计算分段、不决定重试和队列顺序。

### GPUI：视觉渲染

- 新建下载和探测结果；
- 独立单任务进度窗口及其准备、排队、下载、暂停、重试、失败、落盘、校验和完成状态；
- 下载完成时把仍然打开的进度窗口原位收缩为完成窗口，而不是再叠加第二个窗口；
- 虚拟化任务列表、过滤、排序和批量操作；
- 任务详情、连接/分段可视化、日志和失败信息；
- 队列、设置与诊断；
- 只做短促的一次性动效，不在空闲状态持续重绘。

## 下载 UI 生命周期（强制行为）

以下流程是下载功能的产品契约，不得用“任务已经出现在主列表”代替：

```text
新建下载
  -> 探测并确认元数据、目标位置和冲突策略
  -> 添加到队列：只进入主列表，不自动弹出进度窗口
  -> 立即下载：进入主列表并打开该任务唯一的进度窗口
       -> Probing / Waiting / Downloading / Paused / Failed
       -> Finalizing / Verifying
       -> Completed
            -> 进度窗口仍打开：原窗口保持中心位置并收缩为完成布局
            -> 进度窗口已关闭：按设置弹出一次被动完成窗口
```

窗口和焦点不变量：

- 同一任务最多存在一个进度/完成窗口；重复打开必须复用并置前。
- 关闭进度窗口只关闭呈现，不暂停、不取消、不删除任务。
- 主列表的双击或“显示下载详情”动作可以重新打开对应任务窗口。
- 手动“立即下载”必须立即给出窗口反馈；真实传输状态只由 Rust 引擎事件驱动。
- 队列后台启动是否自动打开进度窗口由设置决定，默认开启；批量启动不得造成窗口风暴或连续抢焦点。
- 完成时如果进度窗口仍存在，只转换这个窗口，不再创建第二个完成窗口。
- 独立完成窗口默认被动显示，不夺走用户正在输入的焦点；同一终态事件只反馈一次。
- 进度窗口标题、正文和 Windows 任务栏进度必须反映真实状态；未知总大小不得伪造百分比。
- 进度窗口和完成窗口由 GPUI 绘制。C# 只执行任务栏状态、Shell 打开/定位、文件拖拽和关机等
  Windows 专属动作。

进度窗口最小信息与动作：

- 文件名、状态、总大小、已下载、当前速度、剩余时间、活动连接数；
- 准备/排队原因，重试原因、次数与退避时间，失败详情入口；
- 暂停/继续、取消、在主列表中定位、打开所在目录；
- 阶段 2 接入分段详情、连接上限与单任务限速。

完成布局必须隐藏传输期标签页和操作，改为显示文件类型图标、完成状态、文件名、最终大小、最终路径，
以及打开文件、打开所在目录、拖拽文件和关闭。尺寸变化采用短促一次性动效，保持窗口视觉中心，
不得先弹第二个窗口再关闭旧窗口。

## 关键 seam

### 调用端到下载引擎

- `DownloadCommandEnvelope { request_id, origin, command }`
- `DownloadCommandResult { request_id, outcome, error? }`
- `DownloadSnapshot { generation, tasks, queues, aggregate_metrics }`
- `DownloadEvent { sequence, task_id?, kind, payload }`

所有命令都具有相关 ID。事件序号必须单调递增；调用端检测到间隙时请求完整快照，不能用不完整增量
继续猜测状态。

### 传输协议 seam

只有确实存在两个适配器时才固定公共 seam。阶段 1 的 HTTP 实现先保持为引擎内部模块；HLS/DASH
进入开发时，再根据已验证的共同生命周期提取协议适配接口，避免为假想协议制造浅层抽象。

### 持久化 seam

生产使用 SQLite，测试使用内存适配器。事务必须同时保护任务状态、分段变化和产物提交记录，避免崩溃后
出现“任务已完成但文件未提交”或“分段已经拆分但数据库仍为旧范围”。

实现记录（2026-07-27）：

- `nxtools-download` 已实现 HEAD 优先的 HTTP 探测；HEAD 被拒绝或元数据不足时使用有界
  Range GET，二者均被拒绝时再使用普通 GET 获取响应头，支持重定向、服务端文件名、大小、

- 响应通过 `Response::chunk` 流式写入任务专属临时文件；完成前执行 `flush + sync_all`，
  最终文件只通过同目录 rename 发布。
- 临时路径、最终路径及提交状态进入 `download_artifacts`。任务状态、传输状态和产物状态由

- 启动时把中断执行恢复为暂停；服务端派生文件名及产物路径可跨重启恢复，取消能清理准确的
  临时文件。
- GPUI 提交、暂停、继续、取消、删除和快照均通过版本化命令入口；事件通道容量为 256，
  进度最多每 80ms 发布一次且只占用前 192 个槽位，关键状态事件通过有界背压保持顺序和可靠性。
  桌面检测序号间隙并请求完整快照，
  空闲时没有固定轮询。
- 新建下载现在先在后台执行版本化 `Probe`，确认服务端文件名、大小、Range 能力、保存位置和
  重复目标后，才允许“加入队列”或“立即下载”。`queue_only` 任务保持 Created，不启动网络；
  “开始/继续”才进入 Probing。
- `DownloadWindowLifecycle` 按任务 ID 保证一个进度/完成窗口。关闭只移除呈现；重开置前；
  完成和失败原位变形，重试恢复进度尺寸；失效的原窗口句柄会被一次终态兜底替换。

  `download.show_completion_window` 默认开启，并兼容旧配置缺少该字段的情况。
- Rust 把任务状态、已下载字节和总量映射为任务栏状态；C# 适配器只调用
  `ITaskbarList4` 继承的任务栏进度方法。

  验证手势仍有效，并在专用 STA 工作线程执行标准 OLE `DoDragDrop`，不越过职责边界。
- 自动化验证：下载/Core/Protocol/Desktop Rust 测试全量通过（Desktop 169 项），
  PlatformHost 测试全量通过；`cargo clippy --workspace --all-targets -- -D warnings` 通过。
