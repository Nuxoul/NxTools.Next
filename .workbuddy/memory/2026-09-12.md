### 关键更正：原生组件到底能不能调尺寸

之前写"尺寸由 `Size` 枚举固定、无法覆盖"**不准确**。准确结论：

- `gpui_component::sizing::Size` **有**自定义变体 `Size::Size(Pixels)`，且有 `impl From<Pixels> for Size`。
- **很多组件实现了它**：`icon.rs:182`、`button.rs:598`、`avatar`、`attachment`、`otp_input`、`number_input` 等。
- **但 `Switch` 没实现**。它的渲染是
  `match self.size { Size::XSmall | Size::Small => (28,16), _ => (36,20) }` —— `Size::Size(px)` 落进 `_`，值被丢弃。
→ 精确说法：**框架留了接口，是 Switch 这一个组件没接上**，不是 gpui-component 整体不能调。
→ **以后判断"能否调尺寸"必须去读该组件 render 里的 match 分支，不能只看有没有 Sizable。**

## B 完成：剪贴板分类 chip → 原生 `Tab`

累计 **7 项**替换。`cargo check --all-targets` 0/0，`cargo test` **366 passed / 0 failed**。

**落地方案（包裹而非替换）**：`gpui_component::Tab` 的 `base: gpui_base::Tab` 是私有字段，
`Tab::new()` 把 id 硬编码成 `gpui_base::Tab::new(0usize)`（**id 是索引**），而 `gpui_base::Tab::id(..)`
存在但上层没暴露。分类 chip 需要唯一 id（拖拽重排 + 右键菜单都是有状态交互）→ 不能把交互挂 Tab 上。
- **外层 div**：保留 `id`（`category-{id}`）+ 全部交互（on_click/on_drag/drag_over/on_drop/tooltip/context_menu）
  + 布局尺寸（`h(BADGE_HEIGHT)`/`w(tab_width)`/`flex_none`）。
- **内层 `Tab::new()`**：只管视觉 `.label().icon().selected().outline().w_full().h_full()`。
- `Selectable` trait 需 import，路径 `gpui_component::Selectable`（由 `gpui_base` 重导出）。

**测试面**：全仓**没有测试断言真实分类 chip 的几何**（`ui/tests.rs` 的 `category-fixture-*` 是独立 fixture，
只覆盖 `resolve_category_wheel_offset`）。→ 无需重校契约。
⚠️ **视觉无测试覆盖**：形态从"6px 圆角+描边+选中淡色底"变成 `TabVariant::Outline`，需人工验收。

## C 第一步完成：M-09 映射表产出（`docs/m09-token-mapping.md`）

**查清一个被误解的前提**：`crate::theme::Theme` 与 `gpui_component::Theme` **不是"新旧两套"**，
而是**同一份 `Palette` 的两条投影**——`theme_palette.rs` 的 `semantic_config()`(:305) 注入语义层、
`to_visual_theme()`(:358) 产出应用 Theme，都从同一个 `Palette` 派生，且注入侧已有测试断言(:472-490)。
→ M-09 的目标不是"改颜色"，而是**消除双份取色来源**。

**缺口分析**（27 角色 / 约 750 处取色，按频次）：**8 个角色在语义层无对应槽**——
高频的是 `border_subtle`(108)、`text_secondary`(59)、`surface_hover`(30)、`element_selected`(21)、`accent_soft`(18)。
原因：`bg_hover`/`bg_active`/`border_subtle` **根本没被注入**；`accent_soft`/`danger_soft` 是 `blend(..,0.22)` 派生色。

**两条路线（待决策）**：
- A（推荐）：先扩充 `semantic_config()` 补槽 → 冻结映射 → 分批替换 → 退役 `to_visual_theme()`。
- B：接受双投影，只约定"新代码读语义层"。零风险但放弃 M-09 收益。

**两个风险**：① **签名级改动才是主体**——组件工厂几乎都收 `theme: Theme`，改读 `cx.theme()` 要改签名+全部调用点，
工作量大于取色本身；② **颜色测试覆盖极低**——366 测试覆盖几何/交互，基本不覆盖颜色，改错测不出来，必须人工验收。
