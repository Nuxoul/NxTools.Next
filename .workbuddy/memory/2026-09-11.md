## 修复两个长期 UI bug（新建下载窗口被裁切 / 链接识别多链接布局错乱）

### Bug 1：新建下载对话框内容被窗口裁掉
- 根因：对话框是固定尺寸不可调窗口，错误行高度预算 `NEW_DOWNLOAD_ERROR_RESERVE_HEIGHT`(38px) 只叠加在紧凑布局(176px)上；probe 确认后的布局实际需要 278px。submit 校验失败时窗口被 resize 到 214px，确认布局(标题栏34+表单192+页脚44=270)装不下，且确认分支 body 缺少 `min_h_0`/`overflow_hidden`，flex 溢出把页脚推出窗外。
- 修复（`downloads/new_download_view.rs`）：新增 `new_download_error_window_size(confirmed)`，所有 submit 错误路径按 `self.probe.is_some()` 选择基础高度；确认 body 加 `.min_h_0().overflow_hidden()` 兜底（页脚永远不被推出）。
- 测试坑：GPUI 测试环境里 `window.resize()` 只改缓存 bounds，不改绘制表面；元素几何断言需先 `window.simulate_resize(...)`。旧测试 `production_probe_summary_uses_narrow_inspector_and_bounded_stage_geometry` 此前"通过"正是因为溢出 bug 把页脚画到了窗口外，已补 `simulate_resize` 修正。

### Bug 2：链接识别面板多链接时下方大片空白
- 根因（`tools/link_panel.rs`）：窗口高度公式 `rows*30 + 24` 与实际渲染不符（行高28、容器py=8、折叠态多链接只渲染1行+24px展开器、页脚22+mt2）。3链接折叠：旧公式114 vs 实际84 → 30px 空白。
- 修复：`link_panel_height(total_rows, expanded)` 按渲染结构精确计算，渲染处改用共享常量防止再漂移；clipboard.rs 两处调用与展开器 resize 同步更新（折叠60/84，展开 38+28n）。

验证：`cargo check -p nxtools-desktop --tests` + 全量 358 测试通过（CARGO_BUILD_JOBS=1 / CARGO_INCREMENTAL=0 / codegen-units=256）。

### 经验
- 固定尺寸 GPUI 窗口的高度预算必须从渲染结构逐项推导，最好让渲染与预算共用同一组常量。

### 0.5.1 → 0.6.1 真实破坏性变更（踩过的坑）
1. **`InputState::set_value` 不再发 `InputEvent::Change`**（0.6.1 里 `set_value` 会临时关掉 `emit_events`；0.5.1 的 `replace_text_in_range` 无条件 emit）。项目 49 处程序化赋值依赖该回调（快速启动面板清空查询后要收起窗口、下载 URL 探测、设置校验）。
   修法：项目内加 `ui::set_input_value` / `set_textarea_value` 包装，`set_value` 后补 `cx.emit(InputEvent::Change)`（gpui 的 emit 是 `pending_effects` 延迟派发，无重入风险）。`replace_all()` 是官方"会发事件"的替代，但会记账 undo，没采用。
2. **`ButtonCustomVariant` 删掉了 `border` 字段**；且 0.6.1 里只有 `Default` 变体或 `outline` 才画边框（button.rs:631），自定义变体一律无边框。项目 6 处受影响（`ui/components/action.rs` 5 处、`downloads/window_support.rs` 1 处），其中 2 处原本就是透明色、无视觉影响。
3. **`InputState::multi_line/auto_grow` 迁到 `TextareaState`**；`Textarea` 没有 `focus_bordered`。
4. `PixelsExt` 移除 → `Pixels::as_f32()`；`Corner` → `Anchor`；`Point.width/height` → `x/y`；`.focus(window)` → `.focus(window, cx)`；`track_scroll(&h)` 取引用；`DisplayId::from(u64)`；`KeyDownEvent` 新增 `prefer_character_input`；`window.draw` 的闭包要返回 `Element`（`Entity<V>` 现在只 impl `IntoElement`，需 `.into_element()`）。
5. `WindowOptions` 新增字段 → 16 处字面量补 `..Default::default()`（注意基 struct 后不能带尾逗号）。

### 最大的系统性差异：边框开始占布局空间
- 实测（`ui/tests.rs` 的 resize 角点探针）：`panel_window_frame` 的 `.border_1()` 让内容区从 100×40 缩到 98×38 并右移/下移 1px，绝对定位的 resize hitbox 由 (84,24) 变 (83,23)；把 `border_1` 换成 `border_0` 立刻回到 (84,24)。
- 即 gpui 0.2.2 下 1px 边框不占布局，gpui-pre(taffy 0.9→0.13) 下会占。**项目里有 145 处 border 调用**，所以这是全 UI 的 1px 级位移来源，也是剩余 7 个几何断言失败的根因（其中 network_settings 那 2 个是 12px 级溢出，需单独查）。
- 注意：不是 `box-sizing` 默认值变化——taffy 0.9 和 0.13 的 `BoxSizing::default()` 都是 `BorderBox`。

### 待办 / 需用户定夺
- 7 个几何失败的处理方向：①接受新引擎几何、更新像素契约；②在生产代码里补偿边框（保 0.2.2 像素保真）；③暂停迁移。

## gpui-kit 0.6.1 迁移：7 个几何失败全部定位收口，358/358 全绿

用户决定：几何差异「逐个核对后更新像素契约」；右键菜单阴影「不 fork，接受 0.6.1 新版阴影」（`vendor/gpui-component-061` 已移出到 /tmp，不再引用）。

### 真正的根因（三类，此前误判为"1px 边框吃掉布局空间"）
1. **`Bounds::contains` 远边语义变更**（影响最大）。gpui 0.2.2 是闭区间 `x <= origin.x + width`，gpui-pre 0.3.4 改成半开区间 `x < ...`（`gpui-pre-0.3.4/src/geometry.rs:1465`）。凡是子元素正好贴齐父容器右/下边缘（`justify_between`、`w_full` 常见结果）的断言都会误报。**这不是布局回归，只是测试断言的取角约定变了。**
   - 新增 `ui::bounds_contains`（`#[cfg(test)]`，`ui/mod.rs`）显式恢复闭区间语义；脚本把测试里 27 处 `X.contains(&Y.bottom_right())` 改成 `bounds_contains(&X, &Y.bottom_right())`（`.origin` 是字段不是方法，两种语义等价，保持原样）。
2. **等价 flex 列的亚像素舍入差异**。`quick_launch` 诊断面板 4 个 `flex_1` 单元格在 1518px 容器里得到 378.5/380/379.5/380，两两比较差值 1.5px > 1px 容差；taffy 0.13 对每个 item 的边缘独立取整。改为与**精确等分值**（容器宽/列数）比较，容差仍 1px —— 比两两比较更严格且与取整方式无关。
3. **taffy 0.9 违反 `min-height` 的压扁行为（真实行为差异）**。网络设置窗口 720×352：`settings_section` = 1(边框) + 26(节头) + 42(行) + 42(行) + 1(边框) = 112px，两段 224 + 2×8 间距 + 18 note = **258px，而视口内区只有 244px**。旧引擎把 14px 负空间摊到 4 个 flex 行上，**每行砍 3.5px → 行高 38.5px**（低于 NxTools 自己声明的 `SETTINGS_ROW_MIN_HEIGHT = 42`）；taffy 0.13 正确把 min-height 当硬下限，于是内容真的超出、走内容区本就声明的 `overflow_y_scrollbar` 滚动。
   - 定量验证：把行的 `min_h(42)` 临时删掉，行自然高正好 **37px**，section 102，inset 18 —— 与"38.5 = 42-3.5"完全自洽。`min_h_0()` 加在 section 上无效（阻挡压缩的是行自己的 min-height，不是 section 的 auto min-size）。
   - 用户决策：**保持 352px，接受滚动**（不加高窗口、不压缩设计间距）。两个测试改为新契约：视口底边贴齐 footer、两类 section 等高、note 仍是最后一行、越界量有界（note ≤ 12px；错误行 ≤ 自身高度），并保留"校验错误必须起始于折线之上"。

## 批次 1 阶段 B：5 套主题落地（已完成）

### 关键发现：不要手写 141 个 ThemeColor 字段
gpui-component 0.6.1 提供**语义主题层**：`SemanticThemeConfig { colors(17 个语义色), radius, spacing, typography, shadow }` + `Theme::apply_semantic_config(&cfg)`，组件库自行派生 `list_active`/`popover`/`tab_active`/按钮变体等全部状态色。这比照抄 141 个扁平字段正确得多。另有 `ThemeRegistry::load_themes_from_str` / `watch_dir` 可加载 JSON 主题（本阶段未用，语义层已足够）。

### 实现
新增 `rust/apps/nxtools-desktop/src/theme_palette.rs`：
- `ThemeId`（OneDark/CatppuccinMocha/Nord/ZedDark/GithubLight，`Default = OneDark` 即规范声明的默认）+ `ALL`/`key()`/`label()`/`is_dark()`/`from_key()`。
- `Palette`：规范的 20 个颜色令牌（hex 常量，取自用户给的 design-tokens JSON）。
- `Palette::semantic_config()` → 17 语义色 + radius/spacing/typography（引用共享令牌常量，不是每主题硬编码）。
- `Palette::to_visual_theme()` → NxTools 自己的 29 字段 `Theme`；规范没有的 8 个字段（pressed/disabled/soft/image_well 等）由规范令牌**派生**（`blend`/`shade`），保证"调色板只需提供规范那 20 个令牌"。
- `main.rs` 接入：`ThemeId::default().palette()` 驱动 `visual_theme` + `apply_semantic_config`，原有 app 专属覆盖（`background`/`window_border` 透明）保持在其后。
- 6 个测试：令牌完整性、key/label 唯一可回环、恰好一套浅色（含亮度校验）、语义配置带对共享尺度、`to_visual_theme` 投影、文字对比度、以及**应用后确实到达 live theme**（`apply_semantic_config` → `semantic_tokens()` 断言）。

### 两个实测坑
- **规范自带的 One Dark 次级文字达不到自己的无障碍声明**：`#828997` on `#21252b` = **4.38:1**，略低于 WCAG AA 4.5（其余主题 ≥6.0，主文字全部 ≥7.22，超过规范声称的 7:1）。保留规范原值，门禁记录该偏差并只允许 OneDark 例外。
- **`semantic_tokens().radius.md` 不是 1:1 读回**：`apply_semantic_tokens` 把语义 `md` 写进 `Theme::radius`，而 `radius_tokens()` 是另一套派生比例（返回 2px 而非 6px）；**spacing 根本不落到 live theme**。断言要对准框架真正设置的字段。另注意 `color_tokens().surface` 实际读的是 `popover`。

## 组件层迁移：`popover.rs` 调研结论（判定为**不应替换**）

AGENTS.md 要求"参考审查是阻塞性前置"，本次照做后发现候选名单有误，逐条记录证据：

1. **`ui/components/popover.rs` 里没有交互式 popover**。只有 `popover_shell`（固定尺寸纯视觉容器：圆角+1px 边框+`surface_raised`+`shadow_md`+`overflow_hidden`，无锚定/无点击外部关闭）和 `list_box`（带滚动条的列表容器）。
2. **交互层本来就是 gpui-component 原生 `Popover`**：`downloads/new_download_view.rs:877` 与 `:1103` 使用 `Popover::new(...).anchor(...).open(...).appearance(false).overlay_closable(true).on_open_change(...).trigger(...).content(...)`。`Root::new(...)` 浮层宿主也已在各辅助窗口就位。
3. **`.appearance(false)` 是刻意的**：框架文档明确 "The popover will not have a bg, border, shadow, or padding."，作者关掉原生外观后用 `popover_shell` 自绘，以精确控制 304×240 / 320×240 尺寸与边框阴影。
4. **新建下载窗口是不透明的**（`new_download_view.rs:2499 = WindowBackgroundAppearance::Opaque`），只有剪贴板面板窗口透明（`clipboard.rs:1000/1888/2521`）。所以 `appearance(false)` **不是**透明窗口导致的被迫妥协，而是外观选择。
5. **替换的实际影响面很小**（1 个测试引用 `download-new-schedule-popover-shell`，4 处引用 content/list 选择器），但——
6. **不推荐替换的理由**：开启原生外观后，popover 的 bg/border/radius/shadow/padding 全部改由 gpui-component 决定，这是**纯视觉变更**，而现有测试只断言几何（content 在 shell 内、shell ≤ 304×240），**对视觉结果零覆盖**——失败模式不可观测。在无法截图验证的前提下提交，违背"不得仅凭编译通过就宣布切片完成"。

结论：`popover.rs` 予以保留（自绘外壳是刻意设计）。**后续更安全的替换目标应选"原生等价物可被测试断言覆盖"的**（如 `list.rs::status_badge` → `badge`/`tag`、`state.rs` → `spinner`/`skeleton`），而不是视觉外壳类。
