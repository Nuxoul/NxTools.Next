# Desktop persistence boundary

Evidence: `repo:rust/apps/nxtools-desktop/src/clipboard_worker.rs`, `repo:rust/apps/nxtools-desktop/src/clipboard.rs#save_clipboard_section`, `repo:rust/apps/nxtools-desktop/src/runtime.rs#DesktopRuntime`.

Current framework source lookup follows [Kit0.10.0/defaultpre0.3.12](../../../../docs/reference-code/gpui-kit-0100.md). Earlier versioned source evidence remains dated; original persistence, Dialog pointer/keyboard dispatch, focus and deferred-owner rules are unchanged.

Desktop composes DownloadEngine/store, FinderCatalog and ClipboardHistory; it is not a new SQL/schema owner. Clipboard jobs own live history connection and stage migration then durable config commit before switching. Query reply validates generation/query/category/scope; retain bounded four-page window and immutable cursor. Ordinary UI save merges only owned Core section; storage_directory remains migration authority. No SQLite wait or file/native IO in render. Tests use actual synthetic worker/config/DB delay/failure; direct rusqlite dependency doesn't authorize UI-owned ad hoc queries. [Shared persistence contract](../../shared/engineering.md).

## Scenario: Reviewed extension data management
### 1. Scope / Trigger
Extension removal, retained metadata review, explicit restore/clear/retry and lazy UUID publication. Evidence: `repo:rust/apps/nxtools-desktop/src/extensions/storage_management.rs`, `repo:rust/apps/nxtools-desktop/src/extensions/service.rs`, `repo:rust/apps/nxtools-desktop/src/main_window/extensions_page/storage.rs`, `repo:rust/crates/nxtools-core/src/extensions.rs`.
### 2. Signatures
`AppConfig::review_retained_extension_data_checked(path,reviewed,storage,package,after) -> RetainedStoragePage`; `remove_extension_data_checked(...) -> (AppConfig,cleanup_pending)`; `restore_extension_data_checked(...,cancelled) -> (AppConfig,cleanup_pending)`; `clear_retained_extension_data_checked(...) -> cleanup_pending`. `ExtensionService::commit_config_with_result` carries the durable result separately from runtime-applied status.
### 3. Contracts
One original application busy owner admits one management operation. Store at most16metadata records, never values; ordering continuation is not authority. Original Core lock rereads registry; service publication lock serializes config commit/runtime publication and lazy bind/exact apply. Restore reserves a fresh UUID, requires current trust/empty destination/quiescent actual IO, and never revives old handles. Clear never rewrites configuration or credentials. Use existing service executor blocking pool(max4) for blocking store/config waits; do not directly block a GPUI background future. Keep busy/capacity until actual completion even after cancellation. Original Settings drafts, DialogRoot/deferred confirmation and default-unchecked clear Checkbox retain their owners; workspace data entry remains available after uninstall.
### 4. Validation & Error Matrix
Stale registry/record -> refuse, require refresh; corrupt config -> retain/error, never default overwrite. Cancel before commit -> no new pointer; actual commit followed by cancel/cleanup failure -> preserve committed fact/pending, never false rollback. Failed deletion retains bytes/slot until physical cleanup. No automatic action replay. Read failure is not empty data.
### 5. Good/Base/Bad Cases
Good: reviewed retained generation restores to fresh UUID; default uninstall retains data and orphan page remains reachable. Base: unconfigured host may remove only a package without data UUID. Bad: ignore real UUID, publish stale cached config, hold a GPUI lease during file locks, or report cancelled work as physically finished.
### 6. Tests Required
Actual temporary versioned files/Core rename and Windows deletion-denial; bounded metadata pages/current stale/corrupt read-no-write; original production TestApp pointer/keyboard/default Checkbox/confirm cancel, orphan access, fresh retry, draft preservation and actual last-action bounds. Real held quota/config locks assert UI responsiveness and busy until release; independent test-only3second unlock watchdog turns scheduler deadlock into failure, never a production timeout policy. Physical/native/visual/installed acceptance is separate.
### 7. Wrong vs Correct
Wrong: `cx.background_executor().spawn(async move { blocking_config_and_storage() })` then release fixture lock from the blocked TestApp scheduler. Correct: `service.executor().spawn_blocking(move || blocking_config_and_storage()).await`, with current-ID result application and actual-work-owned resources; original Core transaction/publication ordering stays unchanged.

Released DialogAction has a parent pointer callback, while GPUI0.3.9 keyboard synthetic clicks invoke the focused child's own listeners. For these custom confirmation footers keep the pointer owner and add keyboard-only public Confirm dispatch in the actual official Button on_click; original on_ok performs current review/once-only submission. Do not add KeyDown/KeyUp listeners or patch vendor. Base DialogClose retains its internal semantic button ID; tests match actual bounds and focus, not a debug selector assumed to be an AX path.
Restore-cleanup-only records deliberately do not appear as restorable data. The same page's explicitly confirmed retry uses AppConfig::retry_extension_storage_cleanup_checked under fresh original config/publication locks. Only previously authorized ClearPending/CleanupOnly obligations are retried; ordinaryRetained data/current installed pointer/config/credentials remain unchanged. Refresh is read-only and must not silently retry.
TestApp's temporary global/application references must be explicitly unbound in fixture teardown before asserting service/storage release. runtime.shutdown() retires runs but is not destruction of the service host; merely retrying creation can exhaust the real process-wide4owner cap across a serial suite. Use a weak probe to assert that the same host disappears after dropping fixture references and draining queued UI effects, with a bounded deadline; do not enlarge production limits or split tests to bypass them.

## Scenario: Archive host tabs and submitted operation preferences
### 1. Scope / Trigger
Archive tab presentation, password focus, extraction defaults or progress completion preference changes.
Evidence: `repo:rust/apps/nxtools-desktop/src/archive/browser_host.rs`, `repo:rust/apps/nxtools-desktop/src/archive/application.rs`, `repo:rust/apps/nxtools-desktop/src/archive/password.rs`, `repo:rust/apps/nxtools-desktop/src/archive/jobs.rs`, `repo:rust/crates/nxtools-core/src/archive.rs`.
### 2. Signatures
`ArchiveApplication::open_canonical/close_browser/close_host`; `ArchiveBrowser::new_hosted`; `ArchiveSettings::merge_extract_preferences(baseline,desired)`; `save_settings(path,mutate)` -> original `AppConfig::update_section`; `keep_job_open(id,value,cx)`.
### 3. Contracts
One browser host holds original browser entities; application retains session/generation/depth/lease owners. New canonical path adds/activates a tab, duplicate activates without another read. Tab close cleans only that session; native X cleans all; old host ID cannot retire replacement. Do not persist tab paths/session. Hosted construction never steals dialog focus or queries Component WindowState before Root exists. Switch hides/clears only old source password input before current content focus; original ticket remains current and no password draft persists. Pending/deferred callbacks check active session/host/generation. Keep existing Tree/row/marquee/preview and password authorization owners.
Extract Remember saves only accepted submission's changed fields relative to baseline under original lock/disk reread; target directory separately opts in and validates existing absolute-path grammar. Here remains source-parent. Cancel/render/picker never writes draft. Explicit progress checkbox saves only its create/extract keep field using original background transaction; saved failure does not alter already accepted task/cancel semantics. Secrets, grants, source identity, ordinals, selection context and running state are runtime-only.
### 4. Validation & Error Matrix
Old/missing or explicit-null optional custom-target ->None; malformed JSON/section or invalid non-null path ->preserved error, never defaults overwrite. Concurrent untouched field ->disk latest. Closed tab/old host/source generation ->no stale dispatch/focus. Native activation acceptance is not foreground evidence. Unknown processed total ->unknown, never invented percent; terminal native committed/verified/skipped metrics are separate from codec progress.
### 5. Good/Base/Bad Cases
Good: different archive same HWND and original per-tab entities, encrypted background prompt waits its tab; progress checkbox survives disk reload. Base: explicit Cancel keeps config and accepted work unchanged. Bad: one HWND per tab, filename-only identity, Root-required has_active_dialog in pre-Root constructor, focus before retiring old password Dialog, whole cached archive-section save or processed==committed.
### 6. Tests Required
Production Tab pointer/close/open request/duplicate-no-read/all-close/stale-host; entity/selection/preview generation retention, pending password before/after switch and fresh unlock gesture. Actual checkbox->section disk reopen, accepted form vs Cancel, stale changed-field merge/corrupt/missing config, honest progress/native result and minimum body/footer hit bounds. Official caption buttons add Tab stops: tests must identify actual semantic focused control, not fixed Tab counts. Scroll over page margin rather than a child Textarea and require target fully inside real viewport before click. Physical/native/DPI/user acceptance remains separate.
### 7. Wrong vs Correct
Wrong: constructor calls Root-dependent WindowExt before attaching Root; repeated Tab3 then Space; cached section replaces disk. Correct: one construction helper with explicit initial-focus policy, host focus after current Dialog guard; actual focused original control; locked changed-field merge/background publication. See original task continuation reports for retained red/green failures and acceptance limits.
