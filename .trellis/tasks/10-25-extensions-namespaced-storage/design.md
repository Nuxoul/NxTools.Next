## Restore transaction implementation invariants (2026-10-26)
Use one durable restore intent and a fresh host-issued UUID, never reactivate the retained source UUID. Reserve the fresh record within the original1024 slots before Core pointer commit; while intent exists, reject old destination access so writes cannot race the emptiness proof. Original config lock encloses fresh full-package/trust/runtime review, owner preparation, pointer commit and fresh reconciliation. Owner global->namespace locks drain actual IO, including abandoned callers. Reconciliation validates all current registry pointers before persisting any transition: old pointer/absent package aborts intent without erasing source; new pointer rekeys source to fresh UUID without copying values. Unexpected pointer/foreign metadata fails closed.
Source and empty destination old UUIDs become bounded cleanup records; retain their slots until actual managed regular backing/lock deletion completes. Never expose cleanup-only records as restorable generations. Failure after Core commit reports pending, not rollback. Explicit retained clear/retry uses exact reviewed namespace/revision/bytes/state under the same original config lock; no speculative erasure or automatic effect replay. Tests use actual versioned files and fresh owners at before/after pointer barriers plus actual Core rename denial; no native UI/product launch.

## Desktop composition invariants (2026-10-26)
Formal GUI/headless construction injects original config path plus AppPaths.data_dir/extensions-data. One existing service publication mutex encloses background Core mutation through runtime/resolver publication, and the StorageHost synchronous bind_and_apply boundary holds that same mutex through actual Core bind and exact runtime snapshot application. No mutex is held across await or GPUI lease; actual bounded blocking worker retains ownership despite caller cancellation. Generic runtime publication keeps full identity checks. Desktop cache projection accepts only an exact None->committed UUID package match and never changes trust/settings/enablement or rebinds an existing UUID. Bounded watch revisions drive later-turn manager and deferred Quick Launch metadata updates without cancelling providers. Resolver routing/receipt identity intentionally excludes data UUID; actual two-task process regression verifies postbinding resolution without invalidating accepted tasks. Startup fresh locked reconciliation runs in background; corrupt configuration never retires/deletes data or rewrites config, and cleanup_pending remains distinct from success.

## Management UI execution boundary (2026-10-26)
The original manager owns an in-window Settings/Page/Group/Item projection and deferred original Dialog confirmations. Workspace access remains available with no installed packages; package Settings links to the same host-only state. Each read holds at most16 metadata records, and a continuation is only an ordering key, never destructive authority. Core reads a fresh reviewed registry under its original lock without rewriting config or triggering cleanup. Restore/clear recheck exact current records; mutations invalidate review and require explicit refresh before retry. Saved/applied/physical-cleanup outcomes remain separate.
Blocking management waits must run on the existing ExtensionService Tokio blocking pool(max4), not directly inside a GPUI background future. TestApp can poll that future on the same scheduler thread that must release an actual fixture file lock; direct blocking caused the observed cancellation test to strand. A test-only independent3second unlock watchdog turns that symptom into a bounded failure; production cancellation never frees actual IO capacity early. No GPUI/framework/vendor patch or new execution pool is introduced.

## Official confirmation keyboard seam (2026-10-26)
Exact released Component0.8.0 DialogAction is a parent div on_click with a private dispatch anchor; the actual child Button initially has no activation callback. GPUI0.3.9 synthesizes a keyboard click only for the focused control's own listeners, not a mouse-style parent click. Keep original DialogAction pointer path and official styled Button; a keyboard-only Button on_click dispatches the public Confirm action from its current focus path into the existing Dialog on_ok. No new key listener, submit owner, focus controller, private API or vendor edit. Original current review and once-only submit latch remain final authority. DialogClose's Base button keeps its own semantic ID, so fixtures match real bounds plus focused state rather than assuming debug_selector is an AX path.

## Explicit cleanup-obligation retry (2026-10-26)
Restore cleanup-only records must stay excluded from restorable metadata, yet their retained lock/file reservations need a reachable explicit retry. The same data page provides a confirmed RetryCleanup action; original Core fresh-registry lock wraps reconciliation of previously authorized ClearPending/CleanupOnly obligations only. Ordinary Retained records remain untouched. Read/refresh never performs this action; UI busy/current review/diagnostic correlation and existing service blocking pool are reused. Actual Windows old-lock deletion denial tests cover stale-registry refusal, committed pointer preserved, pending capacity retained, cancel-no-effect and explicit successful cleanup without config rewrite.
