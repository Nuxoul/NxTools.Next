## 1. Architecture, ownership and compatibility

Reuse nxtools-extensions for host-neutral contracts/identity/budgets/runtime state; Core for original locked extension config transactions; Desktop ExtensionService/FeatureAdapters for service composition; Clipboard worker for item/assets/derived commits; NetworkPolicy for outbound route; Finder for ranking; original authenticated Indexer connection/executor for indexed queries. C# original demand broker/process runner owns ordinary Windows processes/Jobs/handles/exit. GPUI original settings/activity/manual feedback renders projections. No dependency cycle, parallel feature store or competing native/clipboard/query receiver.

Add optional strict manifest fields; absent/default values serialize away exactly as before. Preserve legacy schema_version1 and original23 methods/legacy arrays/default-once semantics, package hashes, original task/receipt/cancel/event behavior. Existing package replacement stays explicit and disabled/untrusted; declaration/runtime changes require new approval. Declared APIs are not a sandbox: current-user scripts retain OS authority. App automatically starting a broker is not permission to run a resident script.

### Explicit transport v2, not raised v1 budgets

`runtime.protocol_version` defaults1 and omits1; `runtime.mode` defaults once and omits once. Resident requires protocol2 and an explicit package-listed `runtime.resident_entry_file`; one dispatcher can route all package handlers by host-supplied handler ID/entry metadata. A v2 once package keeps existing per-handler entry_file. No legacy package is silently upgraded or resident.

Protocol2 remains strict UTF-8 JSONL with256KiB per frame. Host creates a random process/session UUID; startup initialize/ready handshake advertises effective limits before invoke. Each request retains full InvocationIdentity(run/correlation/generation/package/handler/hash); v2 frames carry exact session_id/run_id. C# broker controls/events distinguish process lease from invocation; Rust alone validates protocol semantic identity. No child-supplied package/hash/credential scope is authoritative. v2 completion is terminal for one invocation, not process exit; once still waits native tree cleanup before publishing success, resident waits explicit request quiescence/finished acknowledgement before slot reuse. Pending host calls/transfers must finish or cancel before request completion; no post-terminal effects/results/progress admitted.

V2 retains ONE broker-event/protocol reader and a bounded in-owner multiplexer: up to8hostcall futures plus4transfer state machines, select over replies/cancel/deadline/data ACK/progress/next frame. Never synchronously await a host operation while excluding frames needed to finish it; no second consumer of BrokerRun.next or Indexer events. Full current identity rechecked before admitting each effect and publishing each reply, no lock/GPUI lease across await; use bounded result channels and control priority. Legacy v1 execution loop behavior remains unchanged. This is required for streamedblob ACK and concurrentHTTP, not generic unbounded task spawning.

Legacy input1MiB/stdout4MiB/stderr64KiB and64hostcalls remain unchanged. For opted-in v2, ordinary control payload keeps1MiB host->script/4MiB script->host per invocation; validated binary chunk frames have a separate decoded16MiB each-direction budget and bounded encoded wire total24MiB each-direction. Native pumps enforce combined outer byte ceilings BEFORE forwarding; Rust separately enforces exact ordinary/data split, lease offset/size and chunk count. Data/control queues stay bounded, control/cancel gets priority between chunks. No per-frame byte logs. If Rust cannot classify a chunk, it is ordinary/invalid, not exempt. Raw upload bytes are counted before base64 decode/allocation; preflight exact encoded length/reserve rejects overflow. Max512chunk frames/run, single chunk<=64KiB decoded, one outstanding chunk per transfer, hard4transfers/run. This is an explicit v2 resource contract, never an exemption from byte accounting.
For v2 required methods, manifest import checks both known methodversion and required transport compatibility; transport1 packages cannot declare v2-only requirements. host.describe includes minimum_transport plus contextual availability and exact budgets. Optional callers on transport1 receive unsupported_transport, never silent fallback. Progress/data frames are not new v1 variants.

Resident cumulative IO uses per-request budgets plus a lifetime256MiB decoded data each-direction ceiling and64MiB ordinary control each-direction ceiling,4h maximum session age and stderr64KiB per process instance. Before invoking a new request, reserve its full remaining per-request allowances against lifetime ceilings; if unavailable, retire idle session and wait actual reap before starting a new one. No mid-request promised budget cut or endless reset. Invalid/unsolicited between-request frames fail the session. Limits observable via host.describe.

## 3. R2 — invocation progress

Protocol2 `op:progress {session_id,run_id,sequence,completed?,total?,message?}`: monotonically increasing sequence; both numeric fields together,0<=completed<=total,total>0, integers<=2^53-1; or both absent for indeterminate status. Message<=512UTF8bytes/plain text/control-free except newline/tab, label as plugin-reported UI-only text. Max256progress frames/run; valid frames beyond10/s are consumed/sequence-checked but coalesced rather than generating per-tick replies or killing an otherwise healthy request, all count toward the256cap. Exceeding total cap is a typed resource-limit/protocol failure for current run/session as appropriate. UI stores only latest and publishes<=4/s, terminal once immediately. Progress never extends deadline, resets cancellation or makes100% a success. No auto notification per tick, no persistent payload history/event emission or highfrequency logs.

Runtime exposes bounded progress subscription keyed full identity; manual activity/feedback observes next-turn through original owner. GPUI official Progress::value / loading, XSmall4DIP, accessible name, original reduced-motion handling. Known percentage only when total supplied; indeterminate/status text otherwise. Tiny inline cards retain bounds/actions; full explanation in existing details. Provider/event/background callers may emit bounded progress but only an existing matching foreground/manual view displays it; no new popup. Legacy result_batch remains unchanged. Red-capable actual process frame->runtime->manual projection->official paint/current-generation test plus late/terminal/flood/deadline/cancel tests.

## 4. R3 — namespaced durable storage

### API and data ownership
New versioned host methods (methodversion1, transport2 availability): `storage.get {key}`, `storage.set {key,value,expected_revision?}`, `storage.delete {key,expected_revision?}`, `storage.list {prefix?,limit?,cursor?}`. Namespace is resolved from host-owned installation UUID, never caller package path/ID. Key<=128UTF8bytes/control-free, JSON value<=64KiB/depth16,<=256keys/namespace,4MiBserialized namespace total. list<=32metadata items/key+revision, no values, opaque cursor60s/current namespace revision; changes retire cursor. JSON null is a value, missing returns found:false. Mutations return revision; optional expected_revision rejects stale write/conflict; no automatic retry or multi-key transaction.

One serialized bounded IO owner (queue32/global blocking<=4) outside UI/async runtime thread; filesystem root supplied by composition under application data, immutable code staging never writable data root. Canonical opaque namespace names and regular/no-reparse checks, existing locked/sync-temp-rename pattern with exact fs2=0.4.3 already locked; no user-supplied filename, SQL or raw DB. Read stable file/version under same namespace lock; global quota admission lock precedes namespace lock with one documented order. Bound file read before parse; corruption retained/error, never reset to empty. Cache<=16namespace metadata entries, not all values indefinitely. Quota128MiBglobal logical durable data including orphaned namespaces; no eviction of user values. Bounded metadata/tombstones<=1024; quota-full is actionable and preserves old data. Physical temp-copy peak may add one namespace budget, explicitly reserved; refuse before write when reserve unavailable.

### Approved lifecycle and truthful failure
Optional omitted installation/data UUID metadata is allocated lazily once via original Core locked transaction for a package using storage; old packages/hashes unaffected. Explicit replacement while installed carries data UUID forward (not ordinary settings/trust policy change). Uninstall commits registry retirement first, making namespace inaccessible; default retains an orphan generation, all retained generations count toward the128MiBglobal quota and1024metadata cap. Never silently evict an older generation or block disabling/removal merely to preserve a new one; pre-reserve orphan metadata when allocating namespace so removal can retire it without new allocation. Existing removal Dialog offers official Checkbox `同时清除扩展数据`, unchecked. Checked clear logically retires immediately then deletes only managed regular namespace after active leases drain; IO failure reports removed-but-data-cleanup-pending with explicit retry, no false rollback/secure erase guarantee. Credential store untouched. Durable orphan-preparation metadata is written before Core removal commit; failed config removal leaves namespace active and never performs clear. On startup reconcile recorded pointer/current registry under original lock: active UUID remains active, absent UUID becomes orphan; never resurrect registry or delete on ambiguous metadata. No deletion on speculative/stale review.

Same-ID reimport gets fresh data UUID, never orphan autoattachment. Existing Settings page shows retained-data metadata and official `恢复保留数据` / `清除保留数据` actions with confirmation. Restore requires current trust and installed target; if fresh namespace contains data, refuse merge/overwrite and ask explicit clear first. Restore switches pointer under original lock after current reviewed metadata check and lease quiescence; failure leaves current pointer/data. Reimport data reads cannot occur before explicit restore. Full-user external tampering is not an ACL security guarantee.

Tests use tempfiles and actual lock/reopen/full quota/concurrent writer, corrupt/error/rename denial, cancel-beforecommit vs committed-later, upgrade/orphan/reimport/restore/clear failure; no real user config or data. No secret/payload log; docs warn tokens belong in credentials.get, storage is not encrypted credential protection.

## 5. Shared v2 binary/blob plane (R4/R5 prerequisite)

### Lease methods
`blobs.begin {length,media_type,sha256}` -> opaque uploadID, exact pre-reservation before dispatch; `blobs.seal {blob_id}` verifies complete length/digest and makes immutable; `blobs.read {blob_id,offset?,length?}` starts ONE bounded download transfer/span<=8MiB, not one host_call per64KiBchunk; `blobs.release {blob_id}` retires access. Sealed handles bind full invocation+installation/content/host origin and access mode, max120s and never beyond invocation lifetime. Cancellation/revoke/shutdown removes logical access; physical backing retained until actual read/commit lease exits.<=8MiB/blob,16MiBaggregate live/run so input+output can coexist,64MiBglobal temporary backing;4slots/run; no automatic eviction of active bytes. Anonymous app-managed temporary backing, no arbitrary path or mmap/native handle passed to plugin; cleanup allowlist only owned regular files. Short blobs may stay in bounded memory, but same global quota counts memory+disk backing once plus fixed chunk buffers and decode reservation.

Protocol2 data frames use session_id/run_id/transfer_id/sequence/offset/base64; host-installed transfer maps opaque ID to actual owner before first chunk. Exact sequential offset/no gaps/overlap, SHA256 and declared length before seal. A read span streams<=64KiBdecoded chunks with one bounded per-transfer ACK/backpressure; malformed/oversized chunk rejected before growing buffer. Chunk exchanges use dedicated data/control framing, not64host_call slots; ordinary begin/seal/read/release still count host calls and total transfers. Never grow MAX_FRAME_BYTES to fit a whole image. SDK handles framing/multiplex while scripts may implement it directly.

### R5 image semantics
`clipboard.image_open {item_id}` -> bounded PNG blob descriptor from original history worker; managed source image only, no path. Revalidate present/nondeleted item/current storage session/full run before resolving; release source lease on terminal. `clipboard.create_derived_image {source_item_id,blob_id}` consumes a sealed image/png blob, validates PNG signature/encoded<=8MiB/dimensions<=8192peraxis/decodedRGBA<=64MiB (<=16Mpx), rejects malformed/animated/APNG, strips metadata by bounded decode+canonical PNG encode through existing image0.25.10 then commits via original worker with host causality. No generic SVG/HTML/remoteimage/gif/video preview/API. Oversize source returns content_too_large; never silently thumbnail/rewrite original. Decoder runs bounded blocking lane/global one image-codec job with128MiBreserved peak (decoded buffer plus codec scratch/bounded output), no render IO; configure decoder allocation limits and bounded encoder sink, reject rather than exceeding reservation. Corrupted output creates no history item.

`clipboard.copy_image {blob_id}` is explicit and requires Clipboard UI owner; validate same bounded PNG then use original C#image-copy suppression/current request/native ACK. Creating derived history does not copy or paste. If existing capture/image native adapter needs a narrow owned-temp seam, add it there, not a new capture engine. Host-confirmed derived IDs/results use original ManualEffects; original item not edited/deleted/markedused. Image/native path rechecked for managed ownership and native cleanup; fulluser process can still access OS independently. Tests real temp PNG/SQLite/native fakeACK + process chunks/forgedhandle/expired/deleted/rootchange/cancel/commit and no actual user Clipboard.

## 6. R4 — proxy-aware HTTP

Request methods GET/HEAD/POST/PUT/PATCH/DELETE; no CONNECT/TRACE/WebSocket/raw sockets.
