# Archive browser / progress / main entry

## Layout and released component selection

- Main archive entry: Open / New / Extract are recognizable primary task commands above recent archive objects; recovery continuation is a separate secondary action and archive preferences remain a subordinate Settings hierarchy. Released Component0.8.0 `button::Button::new().label().outline().with_size(Size::Medium)` and `list::ListItem::new().suffix(...)` retain original click/focus/owner; the `SettingPage/SettingGroup/SettingItem/SettingField` compound stays the settings owner. The page arranges controls in GPUI divs; no `Toolbar.child` transformation removes their outline. Recent row actions use Small outline and do not open from a plain clickable text row. Empty/loading/failure are distinct; no render-time scanning or native admission.
- Browser: existing released `toolbar::Toolbar::content` carries real outlined Medium actions, deliberately bypassing `Toolbar.child` -> ghost/compact; `menu::{PopupMenu, PopupMenuItem, DropdownMenu}` remains the sole keyboard-capable menu owner. Primary Open / Extract / New / Add / Delete / Test are followed by subordinate View and specialized edits. Released `list::ListItem::selected` with original `BrowserModel`, Tree, resizable panels and selection-driven preview stay unchanged. Existing 64-DIP icon-over-label toolbar is an approved screenshot-specific action layout; Medium identifies the official variant, not an invented substitute. Disabled edits retain the capability explanation tooltip; no unsupported format editing claim.
- Progress: released `progress::Progress::value` only when total is known, `loading` only for actual work and motion allowed; actual member/stage and terminal facts remain first. `collapsible::Collapsible::new().open(...).content(...)` with an explicit Small outline `Button` trigger keeps native commit/error IDs available on demand rather than above recovery; native failure/recovery/warnings stay visible. Footer Medium outline pause/cancel/background and live Resume remain the original Job owner; fresh-operation HZ5 continuation stays on the main entry, never mapped to live Resume.

## Reference and lifecycle boundary

`docs/reference-code/archive.md` records Bandizip public resources (Open / Extract / New / Add / Delete / Test, selected extract, progress pause/stop), no legacy NxTools general archive window, Archiver `AppWindow::new -> wire_callbacks -> ui.run` and SupaZip `App::default -> eframe::run_native`. Read-only recheck of Archiver GUI main/view/Slint, SupaZip nested GUI main/controller and Bandizip Chinese resource entrance confirms the existing note; no source/UI was copied. NxTools `ArchiveApplication` owns browser generations, delayed shell/entry and real Job source/native command; browser view only renders and defers cross-owner actions. Main window only arranges direct existing archive entry commands. Preserve Tree/list navigation, modifier selection/marquee, 4-DIP held-left OLE, codepage refresh, passive selection preview and stale-source rejection. Close/cancel retain native lifecycle and previous snapshot only as visibly read-only until refresh. Progress can hide diagnostic detail but not real failure, cleanup uncertainty, HZ5 irreversible consumed source or fresh continuation guidance. HZ5 uses an explicit new Start with persisted recovery ID; ordinary extraction preserves source, and progress cannot infer committed output or bytes reclaimed from processed work.
