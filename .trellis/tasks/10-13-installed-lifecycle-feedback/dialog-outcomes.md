## Deterministic root scheduling defect (proved before fix)
The previous EventWindow activation caller queued Task.Run -> ExplorerWindowAdapter.TryGetCurrentDirectory. The latter admits concurrency 1 under key NxTools.ExplorerCurrentDirectory with a 750-ms logical bound. A known-dialog return consumed AutoQuickSwitchTracker's candidate and independently tried that same key with an unresolved path. Busy rejection retired the only candidate; later activation completion only published the bar source, never retried the consumed return.

Added an isolated EventWindow constructor injecting only capture, background scheduling, deferred delivery and foreground validation (no HWND/hooks/listener). The production source observation and ProcessRecognizedFileDialog/QueueAutoQuickSwitch callers are exercised unchanged by the repro. Hold fake activation capture at a barrier; deliver known-dialog return; attempt queued capture work while occupied; release activation; drain actual completion/publication. Before scheduling repair the exact fixture failed because zero switch events were emitted. This is a production-caller race repro, not a runner-only assertion and not an installed latency measurement.

## Repair
EventWindow owns one active capture operation, one coalesced source epoch and one return intent using the existing AutoQuickSwitchTracker candidate/generation. Completion returns through existing WmDirectorySourceResolved. No new persistent STA/thread, timer, global poll or directory cache. A return does not race an occupied capture; it schedules one fresh read after activation completion (even if an activation path is already ready, since Explorer may have navigated). Success publishes exactly one typed switch request only for the current candidate and foreground target. Preserve original acceptance timestamp for Rust's existing request-age guard. Failure/full event queue/cancellation clears the one-shot intent without retry loops. The existing bounded native runner still retains its slot for an uncooperative timed-out call; this repair does not interrupt or replace such a native worker.

Diagnostics: quick_launch.explorer_source_accepted/start/ready/terminal share operation correlation and report elapsed_ms, source_epoch and fixed outcome/exception type only. No paths/titles/raw COM messages. Terminal requested means the typed event was admitted, not verified dialog navigation. No native error code is available from the existing bool/string capture API; its null/failure is recorded as capture_failed, not a fabricated Win32 code. Later protocol/navigation commands retain their existing correlations and native-code diagnostics; no end-to-end wire correlation was introduced in this scoped fix.
