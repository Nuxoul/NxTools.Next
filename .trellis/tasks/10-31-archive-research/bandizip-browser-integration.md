## Connected browser path: Find → matches → selected action

- `CFindDlg::vftable` → `FUN_140110610` constructor → archive-window `FUN_14013b940` constructs a **modal** `DialogBoxParamW(...,0xcd, GetActiveWindow(),...)` [E1,E2]. `FUN_140110940` localizes dialog 0xcd, binds its result list (`+0x160`), and adds pathname/packed/original/type/modified columns [E3]. The language resource labels the query field and separate **Delete**/**Extract** buttons (`SimpChinese.lang:830–835`). This is not a modeless search overlay.
- `FUN_140111260` clears/repopulates the result list by walking the archive interface `+0x68` count and `+0x70` member-by-index. Empty query adds every entry; nonempty query uses one of two branches selected by `CFindDlg+0x2c0`: substring search of the member path (`FUN_1401f5a20`) or `PathMatchSpecW` of the derived member name against the query; accepted entries pass through `FUN_140111ab0`. It re-reads the edit control during traversal and stops if the query changed, instead of continuing to publish an obsolete search [E4]. Exact case-folding and query UI option names were not established.
- `FUN_140112c50` takes **selected list-view rows** (`LVM_GETNEXTITEM 0x100c`), reads each row's `lParam` (`LVM_GETITEMW 0x104b`), resolves the *original archive catalog index* through the same `+0x70` accessor, skips entries marked with `0x10`, and appends original indices into the action vector [E5]. The delete call preserves the dialog pointer in `RCX` at the actual callsite [E24]. Find results therefore are not themselves the extraction index space.
- **Extract:** `FUN_140112790` obtains that selection vector and calls the shared `FUN_14013ce80` extraction coordinator with source/archive and selected indices [E6,E7]. **Delete:** `FUN_140112eb0` requires a nonempty selection, asks `TEXT_ASK_DELETE_FILE`, constructs a `del(find)` edit action, invokes `FUN_1401506b0` on the originating archive, then refreshes the Find projection via `FUN_140111260` [E8]. The archive editing format restrictions and update/commit engine are beyond this path; resource buttons alone are not evidence of unrestricted editing. **Navigate to result:** after modal result `1`, `FUN_14013b940` checks the result's originating archive in the open-archive collection, selects the folder in the tree (`TVM_SELECTITEM 0x110b`) and selects the file in the browser list [E2]. Cancellation/close does not run that selection path.

## Opened entries, temporary files, child exit, edit intent

- `FUN_14014f620` prepares a temporary path from the archive path plus `.temp` [E13]. The external-launch helper `FUN_140161eb0` has `CreateProcessW` and `ShellExecuteExW` branches and records source, extracted path and process association; it also polls existing child records before reuse [E14]. [Nested-entry writeback](bandizip-nested-writeback.md) connects command `0x81ef` to selected-member extraction and mode3 launching this application's own executable; ordinary associated Open and mode2 external Edit remain separate.
- On a tracked child's termination, `FUN_140163120` uses `GetExitCodeProcess` (still active=`0x103`), closes process/thread handles, reopens the extracted file and compares its last-write `FILETIME` with the recorded time. A changed file is enqueued for later attention; an unchanged file either passes its path to a global queue or is staged in its record with state `10`, according to `deleteTempFileWhenChildProcessExit` (`+0x4d0`); this alone does not establish actual removal [E15,E11]. This is **exit-time polling**, not evidence of a filesystem change-notification subscription. The `FUN_14013b470` window path checks the active archive/path, restores a minimized owner, brings it forward and asks `TEXT_ASK_APPLY_MODIFIED_FILE`; only Yes enters the follow-up context branch [E16]. The prompt is a choice, not an unconditional overwrite.
- On Yes, `FUN_14013b470 → FUN_14014f8d0` constructs the changed-file edit request and hands it to `FUN_14013be50`, then invokes edit completion `FUN_140154650` on the admitted path [E25,E17]. Immediate refusal deletes the temporary path; non-Yes clears the pending record without submitting the edit. Completion checks temporary open/configured test before moving original→backup and temporary→original, then reopens and requests backup cleanup. [The replacement trace](bandizip-nested-writeback.md) records second-move restoration's unchecked return and the per-parent confirmations; this is not an atomic all-ancestor transaction.

## Smart destination: catalog shape to actual operation path

In `FUN_14011acd0`, target mode2 calls `FUN_1400d19c0(archive, settings+0x294)`. A true result appends an archive-derived name to the base destination; mode3 takes that named-subdirectory branch unconditionally. The resulting destination is written back to the original operation descriptor before worker start. Evidence: `bandizip-operations-code-0x14011acd0.json`, `ev_aa275fd4da73e76d1c99ece289793ce0fc28ebc21a801cf80bd29fde6f087092` (normalized pseudocode lines495–577).

`FUN_1400d19c0` returns false for no usable opened catalog. With one member, it requests a subdirectory only when the single-file setting is enabled and that member is not a directory. With multiple members, it invokes `FUN_1400d1680` and negates its shared-root result. That helper derives the first root component, constructs a directory-terminated prefix and checks the remaining catalog paths against it, adding a terminator for directory records. The inspected comparison is literal UTF-16 code-unit comparison, not a demonstrated case-folding policy. Thus a single root directory can extract directly; a lone regular file follows the setting; multiple entries without one shared root obtain the archive-derived subdirectory. The predicate reads the opened archive catalog, not a selection-local rewritten catalog.
