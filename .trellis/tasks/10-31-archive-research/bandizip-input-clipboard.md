## Clipboard: archive selection → actual data object

RT_MENU 162 and 173 bind Copy Files `0x81e4` and Paste Files `0x81e7`; main dispatch `FUN_14013fc40` indexes `0x1401414e8 + command - 0x8113`: case `0x1c` checks list focus and nonempty selected count (`LVM_GETSELECTEDCOUNT`), then calls `FUN_14014bc10`, while case `0x1d` calls `FUN_140154100` [M,E1–E3]. This distinguishes toolbar/list focus behavior from a generic text-field Copy.

`FUN_14014bc10` checks the active archive reader, creates selected-extraction descriptor type `5`, obtains the browser/source path, invokes shared extraction coordinator `FUN_14013ce80`, and continues only when its two outcome fields indicate no failure. It then enumerates selected list rows (`LVM_GETNEXTITEM`) through `FUN_1401a6770`, builds extracted paths from the selected temporary destination plus reader-resolved member names, and passes those **filesystem paths** to `FUN_140035ad0`; it releases temporary list nodes and descriptor after the attempt [E4]. This is not a clipboard containing decoded ZIP bytes nor a mere deferred extraction promise. The temporary destination and cleanup owner are resolved below. Original row/source binding is retained at the selected-extraction coordinator; generated filesystem paths, not original catalog indices, are the clipboard payload.

`FUN_140035ad0 → FUN_140052da0` creates a `DROPFILES` header (offset `0x14`, `fWide=1`) and double-NUL-terminated UTF-16 path list in HGLOBAL, puts it in an `XDataObject` as `CF_HDROP=0x0f`, `DVASPECT_CONTENT`, `TYMED_HGLOBAL`, and adds registered `Preferred DropEffect` with a four-byte value `2` (MOVE). Successful `OleSetClipboard(dataObject)` transfers a live OLE clipboard object, not `SetClipboardData(CF_UNICODETEXT)` [E5,E6,E7]. On failed `SetData`, the medium is released; on failed clipboard publication the object is released. The OLE object carries an HGLOBAL path list; it does not own the extracted filesystem directory. Clipboard replacement releases the OLE data, not the files; the process-level directory owner is resolved below.

**Exact copy destination and cleanup.** In `FUN_14014bc10`, `FUN_1400ce7c0(&local_268,1)` supplies the value copied into extraction descriptor `local_138`; the same `local_138` is used when joining original-member names for `CF_HDROP`. The coordinator `FUN_14013ce80` consumes the descriptor destination at `param_3+0x10`, returns completed extraction/output state, and does not substitute the containing archive path as destination [E4,E24,S1]. `FUN_1400ce7c0 → FUN_1400ce6f0` reads the configured temp-path switch/settings `+0x4b0/+0x4b8`; when disabled/invalid it calls `FUN_140022ed0 → GetTempPathW`. It constructs an available directory with literal `%sBNZ.%x%x\` (base path, tick-count-derived components/collision counter) and `CreateDirectoryW`; **only after successful creation with argument `1`** it appends that directory to application-global `FUN_1401285c0()+0xe8` (tail `+0xf0`) [S1–S3]. A failed `CreateDirectoryW` returns the base temp path rather than registering a `BNZ.*` directory; if subsequent extraction succeeds there, that fallback is not covered by this registered-directory cleanup [S1]. This source/settings/call chain, rather than the Copy menu label, establishes the destination.

On the normal application main-loop return, `FUN_1401329c0` calls `FUN_1401285c0 → FUN_14012a440` [S4]. `FUN_14012a440` iterates global `+0xe8` and calls `FUN_140025b80` on each saved temp directory; that helper enumerates descendants and calls `DeleteFileW`/`RemoveDirectoryW` (with a permission-attribute retry), then clears the queue. The same cleanup also searches `BNZ.*` under the configured/default temp base and attempts to remove matching directories [S5,S6]. This is **application-level cleanup on ordinary loop exit**, not `IDataObject::Release` or clipboard replacement; forced termination, locked files and ignored filesystem deletion failures are not successful-cleanup evidence. The destructor `FUN_140128650` merely releases remaining queue nodes/strings; it does not substitute for `FUN_14012a440`'s filesystem cleanup [S7].

**Ctrl+V.** `FUN_140154100 → FUN_140035cc0` calls `OleGetClipboard`, requests `CF_HDROP=0x0f`/HGLOBAL, reads `DROPFILES.fWide` and its UTF-16 path list, then requests `Preferred DropEffect`. It releases both successful `STGMEDIUM`s and the `IDataObject`; it dispatches only when there is a nonempty list and `(effect & 3) != 0` [E8,E9]. The clipboard parser's returned success is set only after `Preferred DropEffect` is successfully read and locked. Thus a conventional HDROP-only producer without that extra format supplies parsed paths but **does not reach Paste** in this inspected call chain. Both COPY (`1`) and MOVE (`2`) effects pass the filter; this caller does not forward the effect to its add/new operation, so MOVE is not itself source-deletion authority [E8,E9].

`FUN_140154100` copies these **external filesystem source paths** to a new list and calls `FUN_14014f660`. If an opened archive passes `FUN_140154360` (ZIP update admission) and `FUN_140153d80` (active-edit/busy gate), `FUN_14014f660` constructs operation descriptor `9`, populates its source list in the archive form, and runs `FUN_1401450e0`; only modal result `1` invokes `FUN_14014f8d0` with current archive path and those source paths. The coordinator hands edit work to `FUN_14013be50`; admitted completion `FUN_140154650` reopens/tests when configured and does the original→backup, temp→original path moves; failures before admission do not publish [E10; existing canonical E23]. An optional delete-original-files flag in the archive form (when chosen) gates a separate post-success source action; the `Preferred DropEffect=2` is not passed as that flag. If no eligible opened archive (or busy), the routine instead posts command `0x8028` for a new archive with no source parameter, or passes supplied paths to `FUN_1401439e0` for new-archive prefill [E10,E11]. This is a **different result path** from add-to-original; a paste cannot be described as unconditional ZIP editing. The ordinary new-archive form reaches create coordinator `FUN_14013d910` only after accepted form submission [E11,E12; existing create report].

## Copy full paths: different data format and naming authority

Menu `0x825f` dispatches case `0x37 → FUN_14014c3d0` [M,E1,E3]. It enumerates selected list rows, obtains their browser item and original catalog index (`item+4`), adds selected folder descendants where appropriate (`FUN_1400ef020`/`FUN_140157310`), then retrieves each original member record from the *active reader* virtual `+0x70(index)`. It sorts gathered names, joins with UTF-16 `CRLF` (`0x140292eec`), and publishes **`CF_UNICODETEXT=13`** via `OpenClipboard(owner HWND) → EmptyClipboard → SetClipboardData → CloseClipboard` [E13]. The strings come from the archive member table; this body does not prepend the containing archive's `C:\...\archive.zip` path or extract files. “Full pathnames” therefore means complete **internal member paths**, including folder components, not absolute filesystem paths. It does not publish `CF_HDROP`, unlike Copy Files. Without selection/reader it does not replace the clipboard. If `OpenClipboard` fails after successful HGLOBAL allocation, the inspected body has no `GlobalFree` on that branch (a small allocation leak per failure); `SetClipboardData` failure does free it [E13].

## Files dropped **into** the archive window

Window callback `FUN_140138140` handles `WM_DROPFILES=0x233` through `FUN_140148740`: busy refusal, owned paths at `window+0x78/+0x80`, `DragFinish`, synchronous `FUN_140148b20` and final clearing [E14,E15]. The separate [Shell/queued-input trace](bandizip-shell-incoming.md) connects the OLE producer `CMainWnd` callback `0x140148a10`, `CF_HDROP` parsing, `PostMessageW(WM_COMMAND,0x8263)` and later `FUN_140148ae0` drain/clear [M,E1,E3,E16]. The queued path is a different application turn, not outgoing `DoDragDrop`. Explorer dropping onto a ZIP uses a third boundary: Shell `IPersistFile` target binding plus `IDropTarget`→EXE operation9, not this window list.

`FUN_140148b20` reads that retained path list/count, uses `FUN_1400d1d00` on the first source to classify directory/archive candidate, consults current reader and location/inside-window state to choose a direct action or create `CAskDropFileDlg`. The form is owner-modal `DialogBoxParamW(template 0xbf)`; its initial action, path/password context and delete-after flag are returned to the owner only when modal result is `1`. Cancel/close leaves the dispatch branch without opening, creating or editing; the outer `FUN_140148740` still releases the HDROP/list [E17,E18]. Resource labels expose Open / New / Add, not evidence of all branches executing for every input. The `CAskDropFileDlg::vftable` first event slot resolves to `FUN_14010d570`; its next slot `FUN_14010d810` is a destructor (calls `FUN_14010d850`), not a second input handler [E19,E25,E26]. The event handler routes initialization to `FUN_14010d8c0`, OK to `FUN_14010dcc0`, Cancel to `EndDialog(...,2)` without invoking the OK reader, and radio/password/show-password events to visibility-state updates [E25,S8]. PE dialog template `0xbf` binds Open `0x4b3`, New `0x4df`, Add `0x507`, password checkbox `0x411`, password/re-entry edits `0x54d/0x563`, show-password `0x412`, delete-after `0x413`, OK `1`, and Cancel `2` [S9]. On OK, `FUN_14010dcc0 → FUN_14010db90` reads checked radio IDs into dialog `+0x48 = 1/2/3`, password enabled into `+0x4c`, show-password `+0x50`, delete-after `+0x54`, and password edit into `+0x58`; if password is enabled it rejects empty/mismatched confirmation before `EndDialog(...,1)` [S8,S10]. The owner copies action/password/deletion context only on modal result `1`; Cancel/close performs no Open/New/Add and does not save checkbox/password state as a source operation [E17,E25,S8].

For accepted action `1`, it calls `FUN_1401579a0` on the selected incoming archive path (open reader and refresh catalog). For action `2`, it calls `FUN_1401439e0` with the retained filesystem source list: that validates/prefills destination/name, constructs the archive form, then `FUN_140144390 → FUN_1401450e0` enters the modal form, and accepted form submission enters `FUN_140144480 → FUN_14013d910`, per-output task worker and test/terminal result [E17,E11,E12,E20; existing create E21]. For action `3`, it constructs a source-record list from the incoming paths, sets edit descriptor type `9`, applies dialog password/delete-after choices, checks busy state, and calls `FUN_14014f8d0` for **this open archive**. That uses the existing ZIP update admission, compressor plan, temporary output and completion owner; closing the dialog or a failed admission does not mean the source archive changed [E17, existing E23]. Open, New and Add are consequently distinct command/worker/result paths, not one drag-and-drop compression action. List node/descriptor cleanup occurs after each accepted branch; `FUN_140148740` calls `DragFinish` and clears the incoming list after processing, including cancel [E15,E17].

## Limitations / next actual boundaries

- The [Shell/queued-input trace](bandizip-shell-incoming.md) connects Explorer ZIP DropHandler registration/interfaces/target serialization and the open-window OLE producer→posted command→drain. It records the EXE OLE medium-release omission and unchecked-post boundary separately from live acceptance. Installed registration, real drop/update results, concurrent inputs and exact operation-9 delete-intent field transfer remain unverified; the Shell DLL does not receive the EXE terminal archive result.
- Clipboard copies target a registered `BNZ.*` temp folder on the normal create-directory path; application loop exit explicitly attempts recursive cleanup. A failed temp-subfolder creation falls back to the base directory without registering a `BNZ.*` node. Clipboard replacement does not remove the generated files, and the static path does not certify cleanup after abnormal process termination or locked/delete-resistant outputs.
- `FUN_14014c3d0` fails to free allocated HGLOBAL on `OpenClipboard` failure; it also requests fixed zero-initialized allocation (`GlobalAlloc(0x40)`) where a movable handle is documented for `SetClipboardData`. Neither failure rate nor live user-visible result was measured. HDROP-only paste rejected by the missing `Preferred DropEffect` is a reachable supported clipboard format case, not a broad claim about all Explorer clipboard formats.
- Creation worker/test/source-delete completion and ZIP edit replacement are connected through their **existing** canonical reports, not newly runtime-verified. Password, edition, concurrent-drop and filesystem failure acceptance remains untested. Product code, binaries, installed settings, archives and services were not changed.
