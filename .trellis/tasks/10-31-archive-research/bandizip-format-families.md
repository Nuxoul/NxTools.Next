# Bandizip format-family open and extraction paths

## Scope and notation

Static reconstruction of `D:\Tool\Bandizip\ark.x64.dll` 7.32.0.1 with Ghidra 12.1.4. Addresses below are DLL virtual addresses; `R/` denotes `evidence/raw/` beside this note. Complete observations are the `R/ark-families-*` JSON records, not the illustrative class names or extension inventory. The independent `R/ark-families-session-snapshot.json` was seeded once from the matching core snapshot; `R/recipes/rea-ark-families-*.json` preserve the REA calls. ## Admission, dispatch and shared boundary

`CArkMan` `0x180006460` obtains a source through `0x180017c30`, then calls `0x18000eb80`. The latter invokes `0x180010dc0` (content/extension classification), stores ID at manager `+0x50`, creates the class below, configures callback, mode and output factory (`0x18001aec0`), hands the input to decoder virtual `+0x08`, and admits the catalog through virtual `+0x10` if no earlier error. The generic `+0x08` implementation `0x180057c80 → 0x180057cd0` retains stream interfaces at decoder `+0x48/+0x50`, seeks to the discovered offset and calls decoder virtual `+0xc8` **once** for format-specific catalog loading. The manager releases its own input reference; selected extraction reuses decoder/member table. The generic decoder virtual `+0x30` is invoked by `0x18005a4c0` for each selected member, and ordinary selection runs `0x180059a90 → 0x18005a120 → 0x18005a4c0`. Multi-interface objects have different vtables for object/base/ISO or solid subobjects: do not substitute a same-named third table for the manager's actual decoder interface. See factory assembly `R/ark-families-asm-0x18000eb80.json`, `R/ark-families-code-0x180057cd0.json`, `R/ark-families-code-0x180059a90.json`.

The factory’s `+0xfc==0` gate refuses IDs `04,07,09,0f,1a` with `0xa0000044`; this is an observed mode/availability condition, not a blanket assertion of edition-specific support. Unknown `ff` returns detection error/default `0xa0000049`; `100/101`, `200–20b`, `21` and otherwise unhandled IDs return explicit unsupported errors (`0xa0000048` or `0xa0000058` for `200–20b`). Thus StuffIt-looking signatures and other recognizers in `0x180010dc0` are **not** proof of readable archives. Detection is primarily magic/header based (`0x180005030`, e.g. ALZ, `-lh` LZH, MSCF, gzip, BZh, XZ, WIM, EGG, Zstd, ARJ, ZPAQ, Debian ar); subsequent `0x180010dc0` checks extension-dependent possibilities (Brotli `.br`, `.iso` sector `CD001`, `.001` split), scans some embedded content and specializes gzip/bzip2 to nested TAR. Recognition, construction, successful catalog admission and successful payload decode are different levels of evidence.

## Three different extraction plans

**Sequential TAR.** `0x18002e500 → 0x18002cac0` consumes 512-byte headers in source order, handles octal sizes, path/name metadata and extended-header records, stores member data offsets/lengths in the shared pointer catalog (`+0x28`, count `+0x34`), and advances over aligned data without eagerly decoding ordinary TAR payloads. Selected `0x180059a90` resolves only selected indices. `0x18002e710` seeks to the retained offset and uses shared 8-KiB Stored-copy `0x18007e180`; sparse records take `0x18002e800`, which runs a bounded 8-KiB piece reader/transform and reports unsupported TAR method `0xa0000048`, truncated input `0xa0000015` and cancellation/error. No claim that every TAR extension or sparse variant works. `R/ark-families-code-0x18002cac0.json`, `R/ark-families-code-0x18002e710.json`, `R/ark-families-code-0x18002e800.json`.

**Nested compressed TAR versus raw streams.** `0x180010dc0` invokes `0x1800106b0` for gzip and `0x1800109f0` for bzip2 to inspect decoded bytes before returning `22/23` rather than the raw `15/16`. `0x18003b5e0` constructs a solid `CArkUnTGZ` with mode 0/1 and retained ring/working buffers. Its catalog `0x18003b830` parses a gzip header in mode 0, builds TAR member metadata via the same `0x18002cac0` parser fed by the decoded reader (`0x18003c3b0` or mode-specific reader), checks the gzip trailer and decoded CRC, and retains member offsets. The selected-range path `0x18003c960` seeks to the retained compressed source position, reconstructs the decoded stream (`0x18003cb70` or bzip2 mode `0x180058720`) and installs `CArkSolidOutStream`: unselected predecessor bytes must advance the decompressor without publishing their files; only selected members obtain outputs via the common factory. This is **not** independent TAR-file seeking into compressed bytes and not proof that catalog and extraction constitute a single decode pass. `R/ark-families-code-0x1800106b0.json`, `R/ark-families-code-0x1800109f0.json`, `R/ark-families-code-0x18003b830.json`, `R/ark-families-code-0x18003c960.json`, `R/ark-families-code-0x18003c3b0.json`.

Raw gzip `0x180028540` creates one synthetic member (name from header/source; `.tgz` becomes `.tar`) with compressed offset and footer CRC/decoded size; selected `0x1800288e0 → 0x18007db60` decodes Deflate, handles concatenated gzip members, compares trailer CRC/size and signals output/decode failures. Raw Zstd `0x180013b00` also creates one synthetic member (`.tzst` name translated to `.tar`, unknown size), while `0x180013e70` processes Zstd/skippable frames to the selected output with error reporting; a `.tar` *name alone* does not establish TAR browsing. For XZ/`.txz`, the `CArk7Zip` route `0x18004c2f0 → 0x18004c7a0` opens an `IInArchive` on `CMyInStream`, reads handler member count/properties, and changes a `.txz`-derived synthetic member name to `.tar`; selected indices pass through `0x18004f0b0 → 0x18004e170` to the handler. Zstd/`.tzst` uses the raw decoder above. Neither route invokes the native `0x18002cac0` TAR parser or exposes nested TAR members in the observed catalog; the inner TAR is the decoded **output file**, not native inner browsing. `R/ark-families-code-0x180028540.json`, `R/ark-families-code-0x1800288e0.json`, `R/ark-families-code-0x180013b00.json`, `R/ark-families-code-0x180013e70.json`.

**Indexed images and volume-sensitive CAB.** ISO `0x1800389a0` scans descriptors and passes directory records through `0x180038e80`, retaining the catalog. Selected `0x180039cd0 → 0x180039a50` seeks extents and reads/writes8-KiB blocks with integrity, progress/cancel and output-error handling. UDF catalog `0x18004a5b0 → 0x18004a6e0` can detect ISO `CD001` and use that parser; selected `0x18004a980` chooses ISO fallback or native UDF `0x18004a9b0`. Native UDF accepts extent types0/1/2, resolves extents through `0x1800553d0` and copies1-MiB blocks; type2 writes zero-filled blocks, type1 skips copying with a final logical-size check, and other types fail `0xa0000019`. Remaining size, input/output and cancellation are checked. `R/ark-families-code-0x1800389a0.json`, `R/ark-families-code-0x180038e80.json`, `R/ark-families-code-0x180039a50.json`, `R/ark-families-code-0x18004a5b0.json`, `R/ark-families-code-0x18004a980.json`.

**WIM routes.** The complete MSWIM header's compression flag selects native ID `1c` or helper-backed ID `1d`. Native catalog `0x180036600 → 0x180036c90 → 0x1800370a0` retains image/resource/name metadata; its selected `0x180036bd0` is Stored copy, not the compressed payload decoder. The [cross-DLL payload trace](bandizip-wim-payload.md) joins compressed classification to `ark.x64.lgpl.dll`, shared/non-solid/solid resources, chunk tables, raw chunks and XPRESS/LZX/LZMS, then resource integrity and native selected-output completion. Full multi-volume Open, every solid descriptor and native hard-link/alternate-stream publication remain distinct coverage boundaries.

CAB catalog `0x180043480` checks `IArkMultiInStream` and loops available volume parts through `0x180043540`. Shared solid engine `0x180077c80` matches selected indices, creates selected outputs only, advances unselected predecessor bytes, updates CRC/progress, closes with metadata and propagates write/cancel/decode errors. Method coverage remains separate. `R/ark-families-code-0x180043480.json`, `R/ark-families-code-0x180077c80.json`.

**`.001` parts and the distinct ZPAQ adapter.** Input `0x180017c30 → 0x180012a20` recognizes `.001` as multi-input pattern `1` and constructs `CArkMultiIn` through `0x180019b20`; `0x1800191b0` formats successor `%03d` names (`.002`, `.003`, …), opens each present part and `0x180018470` appends its length to the logical stream. Missing/error parts terminate or report through the multi-input owner. Detection `0x180010dc0` can select ID `13` for `.001`, whose `CArkUnSplit` decoder table `0x1801f4650` runs `0x18004a220`: it strips the last extension from the source name and creates one member spanning the aggregate input. Selected `0x180036bd0` seeks the aggregate stream and copies it through `0x18007e180`; stream seek `0x180018280` maps logical positions across part offsets. This adapter does not parse the concatenated payload as an inner archive. ZPAQ IDs `2e/2f` construct `CArkUnZpaq` (`0x180048bc0` sets mode); its `0x1800815c0 → 0x180081700` catalog initializes a `ZpaqInput`/`libzpaq` reader and catalog entries, and its `0x180048fc0` selected routine routes single/history cases to `0x180080bb0 → 0x1800801d0` or dependency/segment cases through `0x180049610`. This is a separate reader and lifecycle from `CArk7Zip`, not a factory-only classification. `R/ark-families-detail-code-0x180012a20.json`, `R/ark-families-detail-code-0x180019b20.json`, `R/ark-families-detail-code-0x1800191b0.json`, `R/ark-families-detail-code-0x18004a220.json`, `R/ark-families-detail-code-0x180048bc0.json`, `R/ark-families-detail-code-0x1800815c0.json`, `R/ark-families-detail-code-0x180081700.json`, `R/ark-families-detail-code-0x180048fc0.json`.

**Unsupported/method-error example.** Bond (`HV30` header) has a real catalog `0x180027790` and selected reader `0x180027f30`: validates chunk/version/method records, refuses newer/unsupported method combinations with `0xa0000200`, streams 4-KiB pieces into the *selected* output with incremental CRC, and checks cancellation/error. Its method/version checks prove why a recognized header and instantiated class do not guarantee extraction of every member. TAR sparse/unknown methods also fail explicitly. Source-wide CRC on every member or a universal codec pipeline is not observed. `R/ark-families-code-0x180027790.json`, `R/ark-families-code-0x180027f30.json`.

The common output factory/writer and terminal close are the previously traced `0x18001aec0 → 0x18001a9c0`, `0x180060920 → 0x180022db0 → WriteFile`, optional `CArkWinOutBuf` queue, `0x180060a10` close/cleanup; generic `0x18005a4c0/0x18005a6a0` checks output/decoded size with format-specific exceptions. Codec/chunk callbacks perform cancellation and integrity at their owner boundaries; no success should be inferred just from a created file. See `bandizip-core-pipeline.md:28–45` and `bandizip-solid-output.md:72–90`.

## Limitations

These are static shipped-binary paths, not fixtures or runtime/edition acceptance. Constructors/vtables establish dispatch, not every encrypted, split, damaged or method-specific archive. TAR.gz/TAR.bz2 have a connected nested path; XZ/Zstd and several adapter/legacy formats lack that evidence. WIM multi-volume admission and complete solid-descriptor construction, the UDF matrix beyond observed branches, CAB methods, non-`.001`/missing split parts and ZPAQ variants remain bounded open questions. No product logic, installation, settings, build or runtime extraction was changed.
