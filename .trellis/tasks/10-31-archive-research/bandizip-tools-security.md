# Bandizip 7.32.0.1 — product tools and security

**Evidence boundary.** Static shipped-artifact inspection of `D:\Tool\Bandizip\Bandizip.exe`, `ark.x64.dll`, and `langs\SimpChinese.lang`: prior REA/Ghidra 12.1.4 records (`ev_…`) plus image-VA x64 instruction traces (`evidence/raw/bandizip-tools-follow-static-*.txt`). Reconstructed binary behavior is not original source or a runtime/GUI test. The EULA constraint is documented in `docs/reference-code/archive.md:7-12`. Neither user credentials nor live configuration/registry values were inspected.

## Password manager: commands, list, persistence

The manager UI contains a password/display-name list, Add/Edit/Delete, and Set/Delete master-password actions; the entry editor accepts an optional display name (`D:\Tool\Bandizip\langs\SimpChinese.lang:538-563`). The window callback `FUN_1401714d0` handles `WM_COMMAND` and on OK (control1) passes its list at `this+0x50` and current master-password state to `FUN_14016fa80`, then ends the dialog. Cancel (control2) ends it without that writer call. Initialization `FUN_140171bf0` loads the manager list via `FUN_14016f1a0`: master-validation mismatch `0x102` opens unlock/retry; other parse failures show a corrupt-data error before offering the prompt. [Password controls](bandizip-password-controls.md) records the exact validation, retry and cancellation path. Evidence: `bandizip-tools-follow-static-passman.txt:304-384,517-724`.

- **Add.** `FUN_140172060` checks the edition field at global `+0x120`: the zero/standard branch refuses a second entry with a license-guide dialog, rather than merely displaying the resource's one-password limit. Otherwise it opens the password/display-name editor (modal result must be 1), requires nonempty password, appends the two retained fields as a 16-byte record to the in-memory list, increments count at `this+0x58`, and inserts its list-control row. Evidence: `bandizip-tools-follow-static-passman.txt:725-787,826-880`; limit copy `SimpChinese.lang:862`.
- **Edit.** `FUN_140172610` validates the selected index against `this+0x58`, preloads both fields, opens the same editor, and, only on a successful nonempty submission, replaces the selected 16-byte pair and redraws its row. Evidence: `bandizip-tools-follow-static-passman.txt:905-1036`.
- **Delete.** `FUN_140172350` collects selected list-control indices. `FUN_140172ce0` walks them in safe direction, removes list-control entries and corresponding in-memory pairs via `FUN_1401700a0`/`FUN_1401701d0`; its move-up/move-down paths also use this selection handler with different actions. Evidence: `bandizip-tools-follow-static-passman.txt:1048-1259,1513-1660`.

On OK, `FUN_14016fa80` serializes the current list and master-password state and calls `FUN_14016fed0`, which writes `REG_SZ` value `data` under **HKCU `Software\Bandizip\passman`**; `FUN_14016efe0` reads the same value. Thus Add/Edit/Delete mutate the dialog list first and persist at OK, not at each button. The window callback does not branch on the serialization/write return before closing, so a failed save is not independently reported there. Evidence: `bandizip-tools-follow-static-passman.txt:3-35,123-198,330-354`; `bandizip-tools-analysis-0x14016fed0.json:145` (`ev_eee6a20ea18b21f1393e614b49924fc68d3a5a1df21ccac37500e726727c0b6e`); `bandizip-tools-analysis-0x14016efe0.json:141` (`ev_c39c92bc9b63124dc7646eebfc429783585f55d55caf50e5faed7a76f9e809ed`). The entry-password dialog separately compares repeated values and rejects disallowed characters before `EndDialog(...,1)` (`bandizip-tools-analysis-0x14016dc70.json:141`, `ev_b9414413ead6c47e33359e9a289195b1f86d40c49f5fd09b2d958124077e0ea9`).

Master set/change/remove update application session state first; manager OK persists the current list with that master, while Cancel does not restore the changed session master. Reset is different: `FUN_140173d60` requires Yes before immediately serializing an empty list, then returns successfully (`SimpChinese.lang:552-556`; `bandizip-tools-analysis-0x140173d60.json:129`, `ev_720869708a528c0c05174c2bd6c21c4dbcd756901e9301026207df69ddd44d14`). The resource warns that storage without a master is unencrypted (`SimpChinese.lang:540-542`). [The control trace](bandizip-password-controls.md) connects version/encoded-record validation and master mismatch without naming an unverified cryptographic primitive or reading stored values.

## Password recovery: GUI control/worker boundary (no attempt)

The five-step workflow Open → Check → Settings → Recover → Done exposes archive selection, character classes/specified characters, thread count, prefix, extension-signature option, Start/Cancel/Pause/Resume and Copy (`SimpChinese.lang:952-1027`). `FUN_1401770a0` handles archive-open canceled/broken/no-password/header-encryption-unsupported/member-not-found states before advancing (`bandizip-tools-analysis-0x1401770a0.json:289`, `ev_879956513a1d636b81d62510c46105c7ab04ef11b365fd7989d48db1ff8a43ea`). HKCU `SOFTWARE\Bandizip\PassRecovery` separately persists the last archive path and the above *preferences*, not a recovered password (`bandizip-tools-analysis-0x14017d1b0.json:129`, `ev_b342f6d76513c609d990d1e63aaed4c2dd03dc7baef594ba02e533a485746978`).

The window callback `FUN_140174780` dispatches command `0x3ff` to `FUN_140178680` (start), followed by state refresh; command 2 confirms exit while work is active, while its separate stop branch calls `FUN_140178600` and updates the view (`bandizip-tools-follow-static-recovery.txt:3-158,207-221`). Start checks for an open encrypted archive and at least one character source; invalid inputs display the corresponding messages. On acceptance it sets UI state 1 (Working) via `FUN_14017a6f0`, copies chosen input/limits into the worker state and starts its retained worker through `FUN_140087830` (`bandizip-tools-follow-static-recovery.txt:740-964`). `FUN_140178600` sets its cancellation field at `+0xa0`, exchanges the worker handle at `+0xa8`, waits with a 5,000-ms bound, and retains a timed-out handle rather than pretending work is finished (`bandizip-tools-follow-static-recovery.txt:2154-2184`). UI state assignment `FUN_14017a6f0` writes `+0xaf4`; `FUN_14017c150` renders 0 Ready, 1 Working, 2 Paused, 3 Stopping, 4 Found, 5 Not Found (`bandizip-tools-follow-static-recovery.txt:1226-1241`; `bandizip-tools-analysis-0x14017c150.json:225`, `ev_bbfb172dc968158dcf95bf4d16afb909b76bb1ea9f27cc5929d0a5bb5f75139c`). The result-facing `FUN_14017a0e0` moves to Found (4), navigates to the Done page, and stores preferences; a separate window callback branch moves to Not Found (5) (`bandizip-tools-follow-static-recovery.txt:1078-1198,220-228`). This traces UI/worker control and terminal feedback, not the worker's password-testing algorithm.

The edition branch in `FUN_140178680` selects Standard one thread versus the paid preference; worker setup caps concurrency at64. Pause/resume uses a shared flag polled every100ms, with no all-worker acknowledgement or separate wake event. The paused page exposes Resume and native Cancel refuses closing while paused; the exposed flow is resume before stop/exit. [Password controls](bandizip-password-controls.md) records those owners. The [length-source trace](bandizip-recovery-length.md) connects a separate provider output through dialog `+0x90` to worker `+0x514`, overriding the constructor's10,000 default. The exact Standard-four-character numeric policy and per-candidate boundary remain unestablished.

## Scan decision/result and extracted-file provenance

- **Security configuration and scan admission.** Settings writer `FUN_14016a570` binds `bCopyZoneIdentifier` to `+0x4a0`, `bScanMalwareBeforeExtract` to `+0x4a4`, and free/paid scan-buffer megabytes to `+0x4a8/+0x4ac` (`bandizip-browser-code-from-0x14016ae74.json`, `ev_f9fb926fd126cdfa26cdb64777d5f3c89aa2efa8a5ca0940a26c332774e531d2`). `FUN_14013ce80` copies the scan setting into operation `+0x11c` under its additional eligibility guard (`bandizip-browser-code-0x14013ce80.json`, `ev_8fc0242fe07fd953b0fc3d22edc0d11b48af88f7d863ef4b6fe346b44acf6f7b`). [The scan data-path trace](bandizip-browser-scan-details.md) connects this descriptor to ordinary extraction's candidate selection and bounded extraction-to-scan stream, separately from the filesystem extraction pass. Scan and provenance are different settings and operations.
- **Actual native Zone propagation.** [The provenance trace](bandizip-provenance.md) connects EXE settings `+0x4a0` → options `+0x54` → IArk slot `+0x150`/`0x1800084a0` → `CArkMan+0x98` context. Context `+0x80` points to a retained byte-pointer/length holder, also owned at manager `+0x130`. Successful Open reads source ADS when enabled; direct and buffered outputs receive the same context and call `0x18000d6d0`. That writer filters target suffixes, writes/flushes the retained bytes and deletes partial ADS on write/flush failure. Source-read failure does not fail archive Open, skipped targets return without an ADS, and the output consumers do not promote the ADS writer return into the main-file result. Provenance is neither universal per-member copying nor a scan verdict.
- **Scan modes and results.** Worker `FUN_1401b3c80` routes operation8 to the scan core and ordinary extraction to `FUN_1401b3ff0`. When scan admission is enabled, the latter filters executable/script/document candidates by original member index, uses the configured buffer limit and calls the same scan core. Member completion reports provider results through `FUN_140187410 → FUN_1401b2df0`; the synchronized list is rendered by `FUN_14011cc50` and the progress terminal. In-process detection increments the count that makes pre-extract handling return before filesystem extraction. Auxiliary verdict mapping is separately connected but not proven equivalent in that count/abort behavior. [Exact records and limits](bandizip-browser-scan-details.md) preserve detection, too-large/skipped, initialization/provider faults and ordinary completion as different results.
- **AMSI process boundary.** `FUN_140186940` constructs the `data\Amsiman.x64.exe` path; request `FUN_140187d70` fills `BANDIZIP_AMSI_MMF_%d` and sends the registered check-buffer message with a five-second bound. `FUN_140187800` requests child exit and waits with its own bound (`bandizip-tools-follow-static-scan.txt:2373-2560,2613-2660,2752-2818,2825-2940`). [The helper trace](bandizip-amsi-helper.md) connects installed helper7.17.0.4 mapping checks, `IAmsiStream` provider calls, request status, verdict/description and parent/exit cleanup. The main helper wrapper does not increment the in-process detection count; its request-failure fallthrough also cannot be treated as an explicit failed member result. Neither RPC completion nor a result-list notification is by itself the pre-extract blocking decision.

## Limitations

Manager unlock/save/reset, recovery pause/resume/stop, provenance settings/source/output propagation and main/helper scan data/results have connected static evidence. The cryptographic primitive, password-testing algorithm and exact Standard-four-character enforcement remain unestablished. Scanner branches differ in detection-count and request-failure handling; no runtime cross-mode scan or blocked-provider cancellation was exercised. No real GUI, user settings/defaults, stored credentials, provider scan or produced ADS was observed; creation/repair are recorded separately.
