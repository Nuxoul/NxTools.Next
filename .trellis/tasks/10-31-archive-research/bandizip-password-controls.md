## Manager unlock, validation, and terminal choices

`FUN_1401714d0` initializes the manager via `FUN_140171960`, then `FUN_140171bf0` reads the session master from the application's `+0x128` field and invokes `FUN_14016f1a0` for the list at manager `+0x50`. The reader clears any previous list, derives a validation/decoding input from the supplied master via `FUN_140170d40`, and reads HKCU `Software\Bandizip\passman` value `data` via `FUN_14016efe0`. An absent/empty value returns a valid empty list. For present data it requires version `1`, compares a stored eight-hex-digit value to `FUN_140021d30` over the master-derived bytes, validates the later hex region's length, converts that region, passes it across `FUN_14002b110` (transformation boundary), and delegates decoded record parsing to `FUN_140170580`. This documents the schema/validation path without claiming an encryption primitive or reading stored values. Evidence: `bandizip-passcontrols-code-0x14016f1a0.json` (`ev_d60b2173c28c7c732019a72f94c80e6e12f5d82afc436912c20eb6bf89302b45`), `bandizip-passcontrols-code-0x140170d40.json` (`ev_5781f1f0772175c19f87d37850bf436de1aafca722ef1c55dd8b036785ac288f`), `bandizip-passcontrols-code-0x14016efe0.json` (`ev_39359e73b521755fdd17558dd7e01c7673cdb1b639d8a9b8b2bbfa5cf2a0d3dd`).

On reader failure, `FUN_140171bf0` treats **only code `0x102`** (master-derived validation mismatch) as retryable: it opens the modal `CPassManMasterPassInput` dialog; its `FUN_140173930` OK action copies the entered master to application `+0x128`, and the caller retries `FUN_14016f1a0`. Prompt result `2` closes the manager with Cancel. Other failures, including unsupported version (`0x100`), malformed encoded region (`0x103`) or a decoded-record failure, display `TEXT_MSG_CORRUTP_DATA` with the error code; the manager then still offers the unlock prompt. Thus a damaged value yielding `0x102` is presented as a master retry, **not** separately diagnosed as corruption. Evidence: `bandizip-passcontrols-code-0x140171bf0.json` (`ev_027cddeb15e093dd5be8fccdf669cf5a8d37280ed123fadd5f6d39a357410710`), `bandizip-passcontrols-static-boundaries.txt:50-132`, `bandizip-tools-follow-static-passman.txt:517-724`.

## Different master-password actions

- **Set/change:** manager command `3` calls `FUN_140173040`; its modal password input must return `1` before the newly entered master replaces application `+0x128` and the button is refreshed. Setting and changing use this same command after manager unlock; editing an individual saved password uses a different entry editor. The new master is persisted with the current list only when manager OK calls `FUN_14016fa80` (then `FUN_14016fed0` writes `data`). Evidence: `bandizip-passcontrols-code-0x1401714d0.json` (`ev_dcedcfb4b8d37de5ba3b10e6b7e99cb553f63b56668e917fde94bd5ee1ce288e`), `bandizip-passcontrols-static-boundaries.txt:3-48`, `bandizip-tools-follow-static-passman.txt:304-385`.
- **Remove master:** manager command `4` clears application `+0x128` and refreshes the button; manager OK then serializes the **existing list** without that master. This does not delete the saved entries. The shipped resource warns that storage without a master is unencrypted (`SimpChinese.lang:540-542`). Evidence: `bandizip-passcontrols-code-0x1401714d0.json`, `bandizip-tools-follow-static-passman.txt:304-385`.
- **Reset after unlock is unavailable:** the unlock prompt's `0x47a` action calls `FUN_140173d60`. After a Yes confirmation warning that all information will be removed, it clears application `+0x128`, writes an **empty list** using `FUN_14016fa80`, and returns successful prompt result; the manager rereads the now-empty store. This is immediate, unlike manager set/change/remove, and is not merely master removal. Evidence: `bandizip-passcontrols-static-boundaries.txt:123-132`, `bandizip-passcontrols-code-0x140173d60.json` (`ev_adfb7acc1b20b41715de46da94c176f1e28beab696c747ccf9b0a49d7916553d`), `SimpChinese.lang:552-556`.

**Product nuance:** manager Cancel skips the writer but does **not** restore application `+0x128` after set/change/remove has already changed it. Its in-memory entry-list changes, by contrast, are not saved on Cancel. The manager OK/reset callbacks also do not check or display the writer's return before closing. A faithful migration needs to decide deliberately whether to reproduce this session-state/save-failure behavior rather than assuming all master changes are transactional. Evidence: `bandizip-passcontrols-code-0x1401714d0.json`, `bandizip-passcontrols-static-boundaries.txt:3-48`, `bandizip-passcontrols-code-0x140173d60.json`.

## Recovery controls: UI command to worker pause and resume

The shipped `data\skin.recovery.data` contains `main.xml` and `main.xs` (retained byte-for-byte as `evidence/raw/bandizip-passcontrols-recovery-main.xml` and `...-main.xs`; readable selected lines in `...-recovery-skin-evidence.txt`). Page 4 has `IDC_BTN_PAUSE OnClick="OnPause();"` and `IDC_BTN_UNPAUSE OnClick="OnUnpause();"`; the script moves STOP → PAUSED and back and dims/restores progress colors. This script animation is distinct from the native work control. Evidence: `bandizip-passcontrols-recovery-skin-evidence.txt` (`main.xml:221-231`, `main.xs:209-267`), `SimpChinese.lang:1011-1014`.

The recovery `WM_COMMAND` callback `FUN_140174780` has the corresponding **pause `0x54e` / resume `0x821e`** cases: pause writes `1` to controller `+0xa70`, resume clears it to `0` and calls the state refresh with Working (`1`). The worker object starts at controller `+0x98`, so these writes target worker `+0x9d8`. Initializer `FUN_14017dad0` clears that field; `FUN_14017ddd0` passes its address to `FUN_14017f550`, which stores it in each subworker at `+0x420`. In `FUN_14017f340`, a subworker tests its separate stop flag `+0x434`, reads the shared pointer `+0x420`, and, **while the pointed-to pause flag is nonzero, sleeps 100 ms and rereads it**. Clearing it allows the subworker to continue its normal event wait/work loop. Thus pause/resume is a **cooperative shared-flag/poll control**, not a pause/wake event or thread suspension. There is no UI-side wait for an acknowledgement that every subworker reached the pause point; pauses take effect at that boundary, not necessarily at the click instant. Evidence: `bandizip-passcontrols-code-0x140174780.json` (`ev_6dff4a603900e153206e7553d51ede98fe772defb1b33c209d440f6a0b2db971`), `bandizip-passcontrols-code-0x14017ddd0.json` (`ev_ecc5521ee588d5f8c0b1a04fb3d79784c2fba6f5569fc99ae8d18983e95addfa`), `bandizip-passcontrols-code-0x14017f550.json` (`ev_f7d6caa90700b798171a5d96445c9917e67875e27a0ab55b786717c15d85eb1d`), `bandizip-passcontrols-code-0x14017f340.json` (`ev_0c9ff4de7812d836ed40a3216c03da66b6d91a9bf87de5dc8d2549f95f2dda17`), `bandizip-passcontrols-pause-length-static.txt:3-137`.

The shared pause flag is separate from the base worker's stop/wakeup events: `FUN_140087830` resets those at worker `+0x50/+0x58`; `FUN_140087940` polls stop and queue wake. Explicit stop `FUN_140178600` signals controller `+0xe8` (worker `+0x50`), sets cancel `+0xa0`, and waits up to5seconds for handle `+0xa8`, retaining a timed-out handle. The subworker stop flag is tested before the pause loop, not within it. Evidence: `bandizip-passcontrols-static-boundaries.txt:136-197`, `bandizip-passcontrols-code-0x140178600.json` (`ev_6410f1158ec6f9922d0d5ce4a751a36bbcb954edbcbb1ce1e07466710b6d614b`), `bandizip-passcontrols-pause-length-static.txt:25-117`.

The paused layout puts Stop/Pause on the running page and only Resume on `PAGE_PAUSED` (`main.xml:225-232`). Script `OnStop()` changes page/color state without calling `OnUnpause()` (`main.xs:240-266`). In native `FUN_140174780`, Cancel command2 ends the dialog only when UI state `+0xaf4` is not Paused (`2`); Working/Stopping additionally ask for confirmation. Ordinary Stop command `0x525` refreshes Ready state, reenables settings through `FUN_140178a90` and calls the bounded stop helper; those UI helpers do not clear the pause flag. The exposed paused flow is **resume, then stop or exit**. Evidence: `bandizip-passcontrols-code-0x140174780.json`, `bandizip-passcontrols-code-0x140178a90.json` (`ev_2f1e77a426a902f398f1fccd2bd3fe4eb57e294dec2c475d1f2f12a49bdd283e`), `bandizip-passcontrols-code-0x140178ef0.json` (`ev_8962677b72dfad6f597e0688afb8029063a2f038a3be048dd73a5ec145908a94`).

## Recovery edition and four-character statement

`FUN_140178680` admits an open encrypted archive and a nonempty character source; on Start it selects controller `+0x588` as **Standard `1` or paid thread preference `+0x38`**, copies worker inputs and calls `FUN_140087830(controller+0x98, HWND)`. Worker entry `FUN_14017e420` resolves automatic CPU count or caps that input to `64` threads before opening `FUN_14017ddd0` and running the plan. These are *thread* settings, not candidate-length limits. Evidence: `bandizip-passcontrols-code-0x140178680.json` (`ev_a90751c598bed713a0ebbca496c7982adf7178abf44cba6de2797d07976a6a40`), `bandizip-passcontrols-code-0x14017e420.json` (`ev_15e9de202795f578e09e5c86d69a00526e90f99f99f468f84e3e896a4145daa2`).

The recovery skin exposes character classes, specified characters and a configurable prefix, but no length/range field. Worker constructor `FUN_14017dad0` initializes `+0x514` to10,000. Its effective operation value is supplied separately: recovery initialization calls the loaded provider's virtual `+0x38` with dialog `+0x90` as an output; Start copies that field to dialog `+0x5ac`, which is worker `+0x514`. The outer plan `FUN_14017e4b0` compares the byte length of its current buffer at `+0x518` against that retained value. The [provider/host trace](bandizip-recovery-length.md) connects the actual value source and batch-oriented scheduling boundary. The aligned character-source field `+0x550` is not a password-length cap.

The shipped Standard up-to-four-characters statement (`SimpChinese.lang:962,998`) is distinct from the thread setting and constructor default. Terminal renderer `FUN_14017c150` selects `TEXT_MSG_NOT_FOUND` for state5 without an edition check; its text is not enforcement (`bandizip-passcontrols-code-0x14017c150.json`, `ev_9718f34fa5e9c219201c6932e3ee69df581c05cc87d6b0aa5b8bfbd0cd827e85`). The separate `data\lm.x64.dll` provider returns the recovery interface and length output. Its recovery slot is identified, but its Standard/paid numeric output and complete per-candidate contract remain unestablished. Neither the 10,000 default nor the outer host check proves a four-character cutoff or acceptance of longer candidates.

## Limitations

Pause/resume, operation stop and provider-to-host length transfer are connected static evidence, not GUI execution or a recovery attempt. Pause has no all-worker acknowledgement or explicit wake event; resumed subworkers poll at100-ms intervals. The exact Standard/paid numeric policy and effective candidate boundary remain unresolved in the [length report](bandizip-recovery-length.md). No real credentials, stored settings, registry values, activation state or target operation were accessed.
