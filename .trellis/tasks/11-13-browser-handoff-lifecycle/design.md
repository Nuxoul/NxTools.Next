# Design

## Owners and change boundary
Browser extension controls Chrome/Firefox download IDs; DownloadEngine owns one correlated controlled handoff and durable task admission; BrowserHost translates Native Messaging commands; the existing Desktop NewDownloadView owns confirmation and resolution. No transport/dependency/permission/native-window rewrite. Existing unrelated dirty source is preserved by local edits.

## Controlled protocol
Native operations are `prepare_browser_handoff` (original payload, openDialog/startImmediately preference), `get_browser_handoff` (handoffId), `commit_browser_handoff` (handoffId, taskId), `abort_browser_handoff` (handoffId). New engine typed commands are BrowserPrepareHandoff{handoff_id,request,open_dialog,mode}, BrowserAcceptHandoff{handoff_id,request,mode,resolution}, BrowserHandoffStatus{handoff_id}, BrowserCommitHandoff{handoff_id,task_id}, BrowserAbortHandoff{handoff_id}. Existing manual BrowserOpenDialog/BrowserSubmit/Blob/batch semantics remain unchanged.

Engine exposes BrowserHandoffState { Pending, Held, Committed, Aborted, Expired, Missing } and outcome BrowserHandoff{handoff_id,state,task_id:Option<DownloadTaskId>}. New private dialog source ControlledDownload(Box<DownloadRequest>) identifies automatic browser ownership; UI submits BrowserAcceptHandoff after original resolution/confirmation and aborts on user close. BrowserAcceptHandoff mode remembers StartNow/QueueOnly/scheduled intent, but holds transmission until commit. Native projection maps Pending to awaiting_confirmation, Held to persisted+accepted, Committed to transferred+accepted, Aborted/Expired/Missing to fixed rejection; every response retains handoffId and taskId when present. Protocol changes are versioned through existing constants, not a fallback compatibility framework.

## Persistence and lifetime
One engine-owned controlled-handoff record persists only identity/state/task/start intent/deadline, never browser credentials or a second task request store. Held acceptance and original task/queue persistence are one SQLite transaction. Pending lease lasts30seconds and status refresh renews it while extension is controlling the browser. Expired/aborted identity rejects late UI acceptance and commit. Held tasks cannot resume or be admitted by task/batch/queue/schedule/reopen before commit. Commit is idempotent; abort is terminal before activation. Preserve original stable browser receipts and task IDs. Storage failures preserve old state and cannot publish success. A committed operation cannot be aborted by an old cancellation request.
Only Pending expires. Held remains durable until explicit Commit/Abort, including browser cancellation followed by worker or desktop restart. Engine command protocol14, IPC6 and SQLite15 version the new boundary; Native Messaging remains protocol2.

Prepare/Accept reuse the existing resolution resource identity: original URL, request context and certificate policy stay bound to the browser item; destination, filename, category, schedule, limits and parsed media selection remain editable. Identity is checked before resolution/admission. Committed task UUID receipts are independent of task-row removal or redownload. Client titlebar/footer cancellation claims Abort before window removal, native close shares the same phase, and acceptance failure ends Pending ownership.

Extension pauses/verifies original download before preparing. Secret-free storage.session journal records browser ID/handoff ID/phase/task ID/start time; no URL/Header/Cookie. One outer native owner spans operation; bounded1second status checks renew the engine lease without per-poll logs. User cancel/failure ends engine operation before resume; desktop unavailable has no late authority after lease expiry. Before browser cancel persist cancellation intent; after success persist browser-cancelled phase before commit. Recovery searches actual browser state and queries same handoff, never guesses from URL/name. After browser cancellation, failed activation stays recoverable without attempting to resume a cancelled browser task. Never remove browser file or erase before successful ownership transfer.

## External resolution
Reuse original window/Root/InputState/Kit0.8.0 controls and original begin_probe generation/cancellation owner. External Url source and reused eligible prefill trigger begin_probe on a later app turn after window/prefill. Manual None source and manual clipboard prefill remain explicit. No layout or visible component variant changes; existing InputGroup and outlined buttons remain. Native topmost/activation/focus and fixed confirmation transition are unchanged.
Component selection remains the locked Kit0.8.0 release: `InputGroup::new(...).input(Input::new(&InputState)).addon(InputGroupAddon::new(...))` with `InputGroupButton` in `InlineEnd`, ordinary opaque input appearance and the original32DIP parent URL tier; original Small horizontal Form/Field, outlined icon actions and primary footer Button remain. Intake136DIP and ordinary confirmation246DIP/media-specific fixed clients, titlebar/scroll/footer, Root and keyboard focus are unchanged. No Toolbar adaptation, custom painted substitute or new variant is introduced.

## Diagnostics
One handoff UUID across extension/native/engine/UI. Fixed control/pending/held/browser-cancelled/committed/aborted/expired transitions and elapsed time; native/SQLite codes at owners. No URL, request/cookie/headers, title/path/body. Polling is quiet. Auto-resolution emits only original accepted/start/terminal lifecycle with source category, not payload.

## References and invariants
Mister extension/background.js:1312,1334,1354,1547 uses Chromium suggestion holding/Firefox pause-resume/early response interception; crates/ipc/src/lib.rs:426-468 acknowledges ordinary commands after channel admission and app.rs:6677/8045 confirms later. Preserve its single-owner control principle, not enqueue-as-durable, ignored cancellation failure/removeFile, POST replay or early download. ABDM and legacy reference chain in docs/reference-code/download.md and task reference-review.md. Browser cancellation remains after durable matching acceptance; rendering/entity callbacks defer cross-owner effects. No real product/package/registration operations.
